Pick a pattern

A worker is your own process that does slow or external work. A live query tells it what to do; a mutation decides whether to accept the result. Nothing new runs inside the database.

Keep a result current

An external value stores each result with the exact input that produced it. When the input changes, the old result stops counting immediately.

This app keeps a SHA-256 digest of every document. Download reactive-worker.ts.

docs/reactive-worker.ts
  • input(ctx, args) returns everything that affects the result: source values, recipe, model and prompt versions, locale, configuration. null means there is nothing to compute. Don't use a global database revision.
  • ctx.get(digest, id) is { status: "pending" }, { status: "ready", value }, or null when there is no input. Read it like any derived value; it stays current.
  • digest.http("digest") exposes digest.pending (the work for one key, or null) and digest.publish. With each, it adds methods for worker pools: digest.next lists stale keys oldest first, and digest.claim, renew and release lease them.
  • publish stores a result only if its key still names the current input, and returns { accepted }. Among racing workers, the first result wins. A result schema checks every value.
  • The input must not depend on its own result. If it goes A → B → A, the stored A result counts again.

Run the worker

docs/reactive-worker-client.ts
  • With args, reconcile keeps one key current by watching digest.pending. Without, it drains every stale key. This client passes lease: true, so copies of it lease keys and share the work; see Shard the work. concurrency runs several computations at once.
  • compute may run more than once for the same input. Failures back off per key, and publications retry with one request ID.
  • Pools notice a key only when its row in the each collection is written. If the input also reads other records, a change there makes the value pending, and digest.pending reports it, but next and claim won't find it until that row changes. Keep pool inputs to the row itself, or run a per-key worker.

Complete every action

When every action matters, create a job in the same mutation as the business change. Workers lease jobs, do the work, and record the outcome.

For example, the mutation that marks an invoice paid also calls receipts.enqueue(ctx, id, payload), so a paid invoice always has its receipt job. Put everything the worker needs in the payload. Queues & expiry has the full example.

  1. Wait and claim. runQueueWorker holds one watch on the queue's ready query for the whole process, and claims only while it has room.
  2. Do the work. Your work(job, signal) runs while the lease is renewed, with every lease the process holds in one call; the signal aborts shortly before the lease would end.
  3. Report through Flower. The worker completes or fails the job with the lease exactly as claimed, retrying lost replies under one request ID.
  4. Drain, then wait again. The worker claims until a claim comes back short, then goes back to watching. How many jobs it runs at once follows the backlog and the process's load.
  • Idempotency: use the business operation's ID across retries and leases; the job ID is a good one. A lease token identifies one attempt, not the operation. Lease expiry can't stop a paused process, so the receiving service must deduplicate or fence. If it fences, keep enforcing after a disaster restore.
  • Retries: the queue's retry policy requeues failed jobs with backoff. Look up an unknown outcome by business ID before calling it failed.
  • The same mutation can update business records when you complete jobs yourself with jobs.complete(ctx, lease, result).

Shard the work

Queue workers share work on their own: each claim leases a job to one process. Reconcile pools need to be told how. Every pool lists the same stale keys, so two pools that read next compute every key twice. Lease the keys, or split them by hash.

Lease keys

Any number of copies
// Start as many copies as you like; they split the stale keys between them.
await reconcile(client, {
  external: "digest",
  lease: true,
  leaseMs: 30_000,
  concurrency: 8,
  signal,
  compute,
});
  • A process claims at most one key per free computation, oldest first, so none hoards work, and the pool evens out as processes come and go. The demo worker leases: start it in two terminals and they share the documents.
  • For a number of computations that follows the work, pass bounds, such as concurrency: { min: 1, max: 32 }. As with queue workers, a process computes more keys at once while keys wait and fewer once its event loop or memory falls behind, reporting each change as a limit event.
  • A process renews all of its leases in one call, every third of leaseMs − marginMs. With 30 s leases, that is one renewal every 8 s per process, however many keys it holds.
  • Leases spread the work; publish still decides. It keeps any result for the current input, leased or not, so a process that wakes after its lease can't store a stale result.
  • If a process dies, its keys wait out their leases, then go back in line. A clean stop hands them back at once. Waiting processes wake the moment a lease or retry delay ends: ready tells Flower when, so nothing polls. Keep leases at 10–30 s: long enough to ride out a leader election, short enough to limit the wait.
  • An edit to a key being computed voids its lease. The new input can be claimed at once, and the old computation's signal aborts at the next renewal.
  • A failed computation hands its key back with a backoff that every process honors, so a bad input isn't retried everywhere at once. The claim's attempt counts tries across processes.
  • Watch digest.stats like a queue's: if the oldest ready key keeps waiting longer, add processes.

Split keys by hash

Hash shards cost no writes beyond publishing, but each key's process is fixed. Use them when computations are so cheap that a claim per batch matters.

One shard of four
// Start SHARD=0 through SHARD=3, each with SHARDS=4.
await reconcile(client, {
  external: "digest",
  shard: [Number(process.env.SHARD), Number(process.env.SHARDS)],
  concurrency: 8,
  signal,
  compute,
});
  • A key's shard depends only on the key and count. Processes agree without talking to each other, and no two shards share a key.
  • Run one process per index, from 0 to count − 1, usually one per machine. concurrency runs computations in parallel inside each.
  • Nothing takes over a missing shard. Restart it with the same index; a Kubernetes StatefulSet's pod ordinals make good indexes. Or run two processes per index: both compute its keys, and the first result is kept.
  • To change count, restart every process with the new value. Nothing is stored per shard, so nothing moves. While old and new counts overlap, some keys are computed twice and others wait. publish still stores only results for current inputs.
  • Each shard's next reads the one list of stale keys and skips the other shards' keys, so more shards mean more reading for every call. Raise concurrency before adding shards.

Split a queue into scopes

One queue serves any number of workers; Worker pools shows how to run them. For a tenant that mustn't hold up the others, or urgent jobs that should go first, you don't need to split it: give jobs a group or a priority (see Order the work). Split it only when some jobs need their own workers: reserved capacity, or a particular machine.

Scoped queue
// In the app: enqueue into a scope, and expose the scope as an argument.
jobs.scope(tenant).enqueue(ctx, id, payload);
define({ uses: [jobs], http: { ...jobs.http("jobs", { scope: "argument" }) } });

// In each worker: claim only from one scope.
await runQueueWorker(client, { queue: "jobs", scope: "tenant-a", work, signal, concurrency: 4 });
  • Each scope has its own order, line, fencing tokens and jobs.stats (pass { scope }). To serve several scopes from one process, call runQueueWorker once per scope.
  • With scope: "argument", any caller can name any scope. To pick the scope from the authenticated caller instead, pass a function; its workers leave scope out. See Leases, retries and fencing.

Spread the writes across groups

Leases, shards and scopes split the workers, not the database. Every claim, renewal, report and publish is a mutation on one Raft group's leader. A busy queue worker renews all of its leases in one call about every eighth of a lease, so 100 processes on 10 s leases send about 75 renewals a second however many jobs they hold, before any claims or reports. With batch, one claim takes several jobs. With wait: true, a job that reaches an idle queue wakes the process first in line rather than every idle one.

When one group can't keep up, give each shard its own partition and spread the partitions across groups. Deploy the app to every partition; each is a separate database with its own queues and external values. Jobs land in the partition whose mutation enqueued them, so point each partition's workers at it:

Workers for one partition
const client = new FlowerClient("http://flower-1:7101").partition("orders-3");
await runQueueWorker(client, { queue: "jobs", work, signal, batch: 8, wait: true });
  • Partition along a line the app already splits on, such as tenant or region, so each mutation stays in one partition. Crossing partitions takes a transaction.
  • Choose partitions when you create the database: data in the default database can't become a partition later.
  • Workers ride out partition moves. Their watches end, and they reconnect with backoff, reporting waiting.
