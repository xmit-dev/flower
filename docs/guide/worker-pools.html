It runs jobs from the queue in examples/workers.ts, on as many machines as you like. Keeping a result current instead of running jobs? See External workers.

How it works

01Waitwatch jobs.ready
→
02Claimjobs.claim gives leases
→
03Workyour code; jobs.renew keeps the leases
→
04Reportjobs.complete or jobs.fail
  • A claim gives one worker a job until its lease ends. Flower decides who gets which job, so there is no coordinator or leader to run.
  • While your code runs, the worker renews the lease. If a worker dies, renewals stop, the lease runs out, and the next claim takes the job again with attempt one higher.
  • A worker that reports after its lease ended gets LEASE_LOST, and its report is ignored.
  • Each process runs several jobs at once: more while the queue holds more than it runs, fewer once its event loop or memory falls behind. One watch and a few claims serve them all.
  • Idle workers wait in the queue's line. A new job wakes the first in line only; if it hasn't claimed the job within a second, any worker may.

The worker

Replace work() with your job. runQueueWorker does the rest: waiting, claiming, renewing, retrying lost replies, riding out outages, and shutting down cleanly. Download job-worker.ts.

Worker settings
Environment variableDefault
FLOWER_URLhttp://127.0.0.1:7101. Any member works; writes are forwarded to the leader.
WORKER_CONCURRENCYUnset: from 1 to 16 jobs at a time, following the backlog and the process’s load. A number fixes it.
WORKER_LEASE_MS10,000 ms per claim and renewal. At most the queue’s lease.maxMs, 30,000 in the example.

Ctrl+C or SIGTERM stops claiming and finishes held jobs. A second Ctrl+C quits at once; the jobs it held run again after their leases.

Try it: kill a worker

  1. Start a local node, then deploy the queue from the checkout:
    Terminal 1 · repository root
    npm run build
node sdk/cli.ts deploy examples/workers.ts
  2. Start two workers, one job at a time each so there is time to watch:
    Terminal 2
    WORKER_ID=alpha WORKER_CONCURRENCY=1 node docs/job-worker.ts
    Terminal 3
    WORKER_ID=beta WORKER_CONCURRENCY=1 node docs/job-worker.ts
  3. Queue 20 jobs:
    Terminal 1
    for i in $(seq 1 20); do
  node sdk/cli.ts call jobs.enqueue "{\"id\":\"job-$i\",\"payload\":{\"n\":$i}}" \
    --request-id "enqueue-job-$i" > /dev/null
done
  4. While they run, crash alpha: press Ctrl+\ in its terminal. That kills it without the clean shutdown Ctrl+C would do. Note the job it last claimed.
  5. Within about ten seconds alpha's lease runs out and the job goes back in line, behind the jobs that were already waiting. Beta logs claimed for it when its turn comes. Check it:
    Terminal 1
    node sdk/cli.ts query jobs.get '{"id":"job-7"}'
# "state": "completed", "result": { "attempt": 2, "handledBy": "beta" }

Run node sdk/cli.ts watch jobs.stats alongside to see the backlog rise and fall.

Pick the numbers

Sizing a worker pool
SettingStart with
Lease length10–30 s. Renewal lets jobs outlast it, so it only needs to cover a missed renewal or a leader election. A dead worker’s job waits up to this long before another worker takes it.
Jobs per processThe default adapts from 1 to 16. For jobs that mostly wait on other services, raise max to 64 or more: the process’s load still holds it back. CPU-heavy jobs in the worker’s own thread stop its growth near what one core takes; run a process per core.
Jobs per claimbatch: 1. With many short jobs, 8–32: fewer claims, and claims on one queue conflict with each other.
Linewait: true once you run more than a couple of processes, so a new job wakes one of them rather than all.
Chained claimschain: true when jobs often wait: each report claims the next jobs in the same commit, so a busy worker spends one mutation per job instead of two. A report whose reply never arrives leaves the jobs it claimed to wait out their leases.
ProcessesAt least two, on different machines, so one crash or deploy doesn’t stop the work.
Worker IDThe default. It is stored on every job the worker holds, so you can see who has what.
RetriesThe queue’s retry policy: five attempts with backoff in the example. Keep the job’s own timeouts shorter than the lease.

When things go wrong

Failures and what the worker does
What happensWhat the worker does, and what you do
A worker crashes mid-jobOnce the lease runs out, another worker runs the job again. Make jobs safe to run twice: pass job.id to external services as an idempotency key.
A job throwsThe worker fails the job with the error message, and the queue retries it with backoff. After the last attempt it stays failed: fix the cause, then call jobs.retry.
Renewals stop landingShortly before the lease ends, the worker aborts work()’s signal and fails the job, which is then retried.
A reply from Flower is lostThe worker retries with the same request ID, and Flower applies it once. Nothing to do.
Flower is down or has lost its majorityThe worker retries with backoff and keeps waiting for work (waiting events). A report that can’t land before the lease ends is dropped (unreported), and the job runs again later.
A worker restarts while a job runs for hoursStopping waits for held jobs to finish, and a process manager may not start the new worker until then. Pass drainMs: held jobs get that long, then their signal aborts and they fail, so the queue can retry them. Work that ignores the abort gets 5 s more, then the worker stops without it and the job runs again once its lease ends. Add release: true when a job cut short is simply unfinished: it goes back to the queue with no error, keeping its place, and another worker runs it again at once.
A service the job calls pushes backCall control.throttle(ms, reason), the third argument of work(): the worker claims nothing for ms and halves how many jobs it runs at once, then grows back slowly.
A paused worker wakes after its leaseIts report gets LEASE_LOST and is ignored (lost). Anything it already did outside Flower stays done, which is why jobs must be safe to repeat.

Know when to add workers

Watch how long the oldest ready job has been waiting. The queue's stats method reports it:

Backlog check
for await (const { value } of client.subscribe("jobs.stats", null)) {
  const waitingMs = value.oldestReadyAt === null ? 0 : Date.now() - value.oldestReadyAt;
  console.log(`${value.readyCount} ready, ${value.leasedCount} running; the oldest has waited ${Math.round(waitingMs / 1000)} s`);
}

If that wait keeps growing, add workers, as long as the services they call can take the extra load. If it stays near zero, you have enough. readyCount, leasedCount and delayedCount count jobs up to 100, and at that value mean at least as many; pass { "countUpTo": 1000 } for more, at a higher cost per update. nextAvailableAt says when a delayed job or running lease next makes work available.

Some jobs need their own workers, or one Raft group can't keep up with the claims? See Shard the work.
