Authenticate and authorize

define({ auth }) and each method’s access compile into one access check. It runs before every public call, retry replay, cached read and watch refresh. Flower compiles it only when a call could be refused: when auth.authenticate or auth.delegation is set, or an exposed method’s access is a predicate. Otherwise every exposed method is public. The access guide walks through an example.

JWT sessions, one public method
import { define, jwtBearer, key, query } from "@flower-js/sdk";

const sessions = key("sessions", { algorithm: "Ed25519", usages: ["verify"] });
const me = query("me", (ctx) => ctx.principal());
const status = query("status", { access: "public" }, () => "ok");

export default define({
  auth: { authenticate: jwtBearer({ key: sessions, audience: ["api"] }) },
  http: { me, status },
});

AuthorizationRequest{credentials: Json, method: string, args: Json, partition: string|null, delegation: {coordinator:string,principal:Principal|null}|null}. method is the alias, or $flower.session.* for retry sessions. credentials defaults to null. delegation is set on participant calls from a transaction coordinator.

  • Credentials are separate from args. A retry with refreshed credentials for the same subject and tenant gets the original result; a different caller can't.
  • Anonymous callers are admitted as subject $anonymous (with the partition as tenant in a named partition), so their receipts never mix with a real subject's.
  • The check reads a fresh snapshot before the call runs. Recheck state that can change in between inside the mutation.
  • An app with an access check reads fresh policy on every call, so even replica-local methods need a quorum. Cached reads also wait for full admission, and some write batching is skipped.
  • Watches recheck on each refresh and close when denied. Data already sent can't be taken back.
  • A trusted coordinator’s principal is admitted in each participant partition with that partition’s name as its tenant.
  • define throws if a method, or auth.sessions, needs "authenticated" access and there is no authenticate.
  • Authorization doesn't secure peer or admin traffic. Protect the network too.

Guard collections

collection(…).access(rules) declares who can read and write a collection's rows and fields. The server enforces it on every read and write a query or mutation makes for its caller. Rules are data, not code: the server folds the caller into them once per call and checks each row natively. The access guide walks through an example.

Owners and admins
import { collection, v } from "@flower-js/sdk";

const notes = collection("notes", v.object({ owner: v.string(), text: v.string(), secret: v.optional(v.string()) }))
  .access(({ principal, row, next }) => {
    const admin = principal.claim("role").eq("admin");
    return {
      read: row("owner").eq(principal.subject).or(admin),
      insert: next("owner").eq(principal.subject),
      update: row("owner").eq(principal.subject).and(next("owner").eq(row("owner"))),
      delete: row("owner").eq(principal.subject),
      fields: { secret: { read: admin } },
    };
  });
APIContract
Collection.access(rules)A new reference with a policy. List it in define({ collections }): a method touching a collection whose policy the manifest lacks throws. A collection has one policy; references without one don't conflict with it.
CollectionAccess<T>AccessRules<T>, or a function of an AccessScope<T> returning them.
AccessRules<T>Optional read, insert, update, delete, write (the default for the last three) and fields. An operation without a rule is denied.
FieldAccess{read?, write?} for one top-level field, on top of the row's rules. Callers who can't read a field get rows without it. write defaults to read: nobody changes what they can't see.
AccessScope<T>principal; row, the stored row (not in insert); next, the row being written (only in insert, update and field write); key, the stored key (a KeyOperand); now, the invocation's time in milliseconds; and all, any, not. Using row or next where it doesn't exist throws at definition time.
PrincipalFieldssubject, tenant, claim(name, …path) and the rule authenticated. Anonymous callers have no subject or claims.
RowFields<T>row(field, …path) or next(field, …path): an Operand typed by the record's field.
Operand<T>eq, ne, in(list), has(item), exists(), lt, lte, gt, gte and startsWith(prefix), each returning a Rule. A missing or null side makes every comparison false, so row("owner").eq(principal.subject) never matches an anonymous caller. Only numbers order against numbers, and strings against strings, by code point; any other pair compares false.
KeyOperandThe row's key as an Operand<string>, plus at(…path): an element of an array key or a field of an object key, for collections declared with collection.key(schema). key.at(0).eq(principal.subject) keeps each caller's writes inside their own keys.
OperandLike<T>An Operand or a JSON value of type T.
RuleA condition, combined with and, or and not.
RuleLikeA Rule, or true or false for everyone or no one.
DerivedAccess<A>derive(name, compute, { access }): who may read the value from a method, as a RuleLike or a function of a DerivedScope<A> returning one. A denied read fails with ACCESS_DENIED. Derived values compute over every row, so give one built from guarded collections a rule; without one, any method may read it.
DerivedScope<A>principal, args (an ArgsOperand<A>), now, and all, any, not.
ArgsOperand<A>The arguments a method reads the value with, as an Operand<A>, plus at(…path) for an element or field of them. args.eq(principal.subject) lets each caller read only its own instance of a per-subject value.
SetOptions<T>{clear?} for ctx.set: fields to remove when the value leaves them out. Hidden fields otherwise keep their stored values; clearing one needs the field's write rule.
AccessManifestThe compiled policy in the collection's manifest entry: read, insert, update, delete and fields rules as JSON.
  • Reads: a hidden row reads as absent and drops out of scans, queries and range pages. Pages skip hidden rows before limit, offset and cursor, so they stay full and a cursor never points at a hidden row. A row found through an index on a field the caller can't read stays hidden too.
  • Writes: a denied insert, update or delete fails with ACCESS_DENIED, and denied inserts and updates fail alike. A denied delete of a row the caller can't see does nothing, like deleting a missing key. A write can't pretend, though: writing to a key that holds someone else's hidden row fails where a fresh key would succeed. Keep each caller's writes inside their own keys, with key.at(0).eq(principal.subject) on [owner, id] keys or key.startsWith(…), and there is nothing of anyone else's to find.
  • A write that leaves out a field the caller can't read keeps its stored value, so a read-modify-write of a redacted row is safe. Make such fields optional in the record schema. To remove such a field, list it: ctx.set(collection, key, value, { clear: ["token"] }). Its write rule decides, so its owner can clear a write-only field ({ read: admin, write: owner }) while other hidden fields stay as they are.
  • Only callers are checked. Derived values, maintenance tasks and the authorization hook run without one and see every row. A derived value's access rule decides which callers' methods may read it: derive("countFor", count, { access: ({ principal, args }) => args.eq(principal.subject) }) gives each caller its own count and nobody else's. Triggers act with the same application rights: their change.before and change.after are whole rows, hidden fields included, and their reads and writes aren't checked against the caller's policy, so a trigger can keep an audit or a counter callers can't write. The method that caused them is back in the caller's view when they return.
  • Policies deploy with the code, atomically, and cached results follow them.
  • A rule that compares now makes the result time dependent, like ctx.now(): it isn't cached, and it changes by itself when the comparison flips, so row("expiresAt").gt(now) hides a row the moment it expires.
  • Rules can have at most 256 nodes, nested at most 32 deep.
  • The test database enforces policies the same way.

Limit how long retry results are kept

By default Flower keeps every retry result forever. Retention lets you drop old ones. It's opt-in and uses numbered epochs, not calendar time:

  1. Initialize retention once.
  2. Issue request IDs scoped to the current epoch, or keep using your own.
  3. Advance the minimum epoch, or have the leader rotate epochs on a schedule. Older scoped IDs are then rejected for good.
  4. Collect the retired results in batches. The leader does this by itself.
APIContract
RetryIdentity{database,incarnation,currentEpoch,minEpoch,epochMs?}. IDs are 32 lowercase hex characters; epochs are nonnegative integers. epochMs is how often the leader advances the epoch, or null when an operator does.
RetentionStateRetryIdentity plus receiptBytes, receiptCount, maxReceiptBytes (number|null), gcCursor (string|null), gcComplete, sessionBytes, sessionCount, gcReceiptsComplete, gcSessionCursor and, while rotating, rotation ({epochMs,keepEpochs}).
RetentionActionOne of: initialize {database,incarnation,max_receipt_bytes}; advance {incarnation,current_epoch,min_epoch}; collect {incarnation,limit}; set_budget {incarnation,max_receipt_bytes}; rotate {incarnation,epoch_ms,keep_epochs}, where the leader advances the epoch after every epoch_ms (at least 1,000; null stops) of its own monotonic time and keeps the last keep_epochs (at least 2) admissible; reincarnate {incarnation,new_incarnation,fence_attestation}, each with operation. Epochs never go down. reincarnate is for disaster restore only, after you have fenced the old cluster yourself.
admin.retentionStatus(options?)Current RetentionState, or null. Admin token.
admin.controlRetention(expectedRevision, action, options?)Apply an action if the revision matches. Returns {state, collected}. After a lost response, check status before sending anything else.
client.refreshRetryIdentity(options?)Reload the current epoch for new request IDs. Doesn't update old IDs. Fails if retention isn't initialized.
client.newRequestId(intent?, options?)Make an epoch-scoped request ID (random intent by default). Save it before sending and reuse it on retry. The same intent in a new epoch is a new request.
RetrySession{database,incarnation,id,epoch,acknowledgedThrough,closed}, owned by the caller's principal. Needs access checks: auth.sessions decides who may use sessions, and the check sees $flower.session.open, .status, .ack and .close.
SessionOptionsRequestOptions plus limit? (default 256 records per call) and abandon? (default false, ACK only).
client.openRetrySession(id?, options?)Open a session. Pick and save your own 32-character hex ID first so you can recover a lost response. Reopening an active session is safe; closed ones can't be reopened.
client.sessionRequestId(session, sequence)Request ID for a sequence number above the ACK mark. You track sequence numbers; the SDK never advances or ACKs for you.
client.retrySessionStatus({id,incarnation}, options?)Current session state, for the owner only. Use it after an uncertain ACK.
client.acknowledgeRetrySession(session, through, options?)Drop results up to through. ACK only after you've saved them. Every result up to that point must exist, unless abandon: true, which also cancels unknown outcomes for good. Retries at or below the mark return ALREADY_ACKNOWLEDGED and never run again.
client.closeRetrySession(session, options?)Close the session for good. In-flight results may be lost. The ID can't be reused.
FlowerClientOptions.boundedRetriesDefault false. When true, generated request IDs use the current epoch. Your own IDs pass through unchanged. The SDK reloads the epoch a quarter of the way through a rotating one; otherwise call refreshRetryIdentity.

Errors to handle:

  • RETRY_WINDOW_EXPIRED: the result is gone. The mutation may still have committed.
  • HISTORY_MISMATCH: the ID belongs to a different database history.
  • RECEIPT_BUDGET_EXCEEDED: new work is rejected; kept results are never evicted.

Your own request IDs keep working once retention is initialized. Each one deduplicates until the floor passes the epoch it first ran in, even across epoch boundaries. After that its result is collected and the same ID runs again, so it is an idempotency key with bounded memory. Receipts from before initialization count as epoch 0. Transactions and staged deployments need scoped IDs. With rotate at epoch_ms: 3_600_000, keep_epochs: 24, every result is kept for at least 23 hours. A disaster restore needs a new incarnation; restoring an old backup as-is is unsafe. Backups may still contain deleted results. Details: retention protocol.

Cleaning up cross-group transactions

Records of finished cross-group transactions are removed only when you close and collect them. Prepared transactions without a decision are never released.
