Values and callbacks

Flower stores JSON. Callbacks are plain synchronous functions over that JSON.

APIContract
JsonThe stored value type: null | boolean | number | string | Json[] | { [key: string]: Json }. Numbers must be finite. Checked at runtime too.
canonicalJson(value: unknown): stringSerializes with sorted object keys; used for identity, equality and typed keys. -0 becomes 0. Throws TypeError for anything that isn’t plain JSON (cycles, depth over 128, BigInt, undefined, class instances, and so on).
  • Encode BigInt, Date, Map, Set and typed arrays as JSON yourself. Use safe integers (such as cents) when you need exact math.
  • Return a JSON value, never a Promise or undefined. Use null for “nothing”.
  • Callbacks have no filesystem, network, timers or wall clock. Use ctx.now() or ctx.clock() for time and external workers for side effects.
  • Each callback starts from a copy of your initialized module. Changes to module globals don’t persist between calls.

Collections and indexes

A collection is a named set of JSON records. Keys are strings, or JSON values checked by a key schema. Indexes find records by field.

APIContract
collection<T = Json>(name): Collection<T>
collection(name, schema): Collection<Infer<S>>		A reference to a collection; it doesn’t contact a server. With a schema, T comes from it and every write is checked: a bad record fails with INVALID_RECORD and details: { collection, key, path }. Missing records read as null.
ref.key(schema): Collection<T, K>A new reference whose keys are JSON values, usually tuples, stored as canonical JSON. A key that fails the schema fails with INVALID_KEY. Scans and ranges return decoded keys.
ref.index(name, fields): Collection<T, K, I>A new reference with one more index on one or more fields of T. Duplicate index names are rejected. Chain it where you declare the collection and use the result.
ref.by(name): IndexA declared index. Unknown names are type errors, and throw TypeError at run time.
Index<T, K, F>eq(value): an equality Query; for several fields, pass a tuple in field order. range(options): an ordered RangeQuery.
Collection<T = Json, K = string, I = {}>Readonly kind: "collection", name and indexes, plus key, index, references and by. A definition, not a client-side table.
Query<T, K>Readonly kind: "query", collection, fields and value. Pass it to ctx.query.
RangeQuery<T, K>Readonly kind: "range", collection, fields and options. Pass it to ctx.range.
IndexScalarnull | boolean | number | string. Sort order: null, false, true, numbers, then strings. Ties break by record key. Records with a missing or non-scalar field are left out of ordered scans.
IndexMapIndex names to field lists: the I of a collection.
FieldOf<T>The field names an index may use: the string keys of T.
IndexValues<T, F>The value types of fields F, as a tuple.
EqualityValue<T, F>What eq and aggregate groups take: the field’s type for a one-field index, otherwise IndexValues.
ScanOptionsOptions for ctx.scan: index (a declared index; omit to walk keys), prefix, one lower bound (gt/gte) and one upper bound (lt/lte) on the next field, reverse, offset and limit. Typed-key collections take a tuple prefix without an index, but reject key bounds with INVALID_SCAN.
RangeOptionsRequired positive limit. Optional prefix (leading field values, typed), bounds, reverse, and after (a cursor from the previous page).
Row<T, K>{ key, value }, with a decoded key for typed-key collections.
RangePage<T, K>rows: Row[] and cursor: string | null; null means no more rows. Pass the cursor as after with the same query. Rows edited between pages can be skipped or repeated.
CollectionManifestReadonly name and indexes, and access and references when it has them: the collection schema as stored in a deployed module.
Declare the schema as part of the application
import { collection, define, query, v } from "@flower-js/sdk";

const orders = collection("orders", v.object({
  tenant: v.string(), state: v.enum(["pending", "paid"]), cents: v.int({ min: 0 }),
})).index("byTenantState", ["tenant", "state"]);

const pending = query("orders.pending", { args: v.string() }, (ctx, tenant) =>
  ctx.query(orders.by("byTenantState").eq([tenant, "pending"])));

export default define({ collections: [orders], http: { pending } });
  • Declare indexed collections: in define({ collections }), in a component, or as the source of an aggregate or trigger. Otherwise queries fall back to scanning, and test databases fail with UNDECLARED_INDEX.
  • A collection name must always carry the same indexes; declaring it twice with different ones is rejected.
  • Indexes don’t enforce uniqueness. A missing field doesn’t match null.
  • Rows and their index entries commit together. Queries inside a mutation see that mutation’s writes.
  • Deploying a new index builds it in one step. For large collections, use staged deployment.

Example: find the first due timer with ctx.range(timers.by("due").range({ prefix: ["pending"], lte: ctx.now(), limit: 1 })). More detail is in INDEXES.md.

References between collections

A reference, or foreign key, says that the rows of one collection hold keys of another’s rows. Flower keeps it whole: at the end of every mutation, each row the mutation wrote refers only to rows that exist, and no row it deleted is still referred to.

APIContract
ref.references(target, on, options?): Collection<T, K, I>A new reference whose rows refer to rows of target. on says where a row holds the target’s key (see ReferencePlace). A mutation that leaves a row referring to a row that doesn’t exist, or deletes a row that is still referred to, fails with FOREIGN_KEY_VIOLATION and commits nothing; details are { collection, key, references, target, targetKey }, with deleted: true for a deletion. Chain it where you declare the collection, once for each reference.
ReferenceTargetA collection, or a function returning one: for a collection declared further down, in another module, or the collection itself.
ReferencePlace<T>A field of T; several fields, in order, whose values make the target’s tuple key; { key: n }, the first n components (1 to 64) of the row’s own tuple key (ref.key(v.tuple(…))); or { key: true }, the row’s whole key, which is the target’s: one row extends another, and both are keyed alike. A single part is the target’s key itself: a string, or any JSON value for a typed-key target. A row whose field is missing or null, or whose key is too short, refers to nothing.
ReferenceOptions{ onDelete?: OnDelete }.
OnDeleteWhat deleting a row does to the rows that refer to it. "restrict", the default: nothing, so the mutation fails while any still does. "cascade": they are deleted too, in the same mutation, and so are the rows that refer to them. "setNull": the fields that refer to it become null (references held in fields only).
ReferenceManifestA reference as a deployed module stores it: readonly target (a collection name), fields or key, and json: true when the target has typed keys.
Keep sessions and their events together
import { collection, define, mutation, v } from "@flower-js/sdk";
import type { Collection } from "@flower-js/sdk";

const orgs = collection("orgs", v.object({ name: v.string() }));
// Each session belongs to an organization, which can't go while it has sessions.
const sessions = collection("sessions", v.object({ org: v.string(), title: v.string() }))
  .references(orgs, "org");
// Events are keyed [session, seq]: deleting a session deletes its events.
const events = collection("events", v.object({ text: v.string() }))
  .key(v.tuple([v.string(), v.int()]))
  .references(sessions, { key: 1 }, { onDelete: "cascade" });
// A collection can refer to itself: name it with a function.
type Folder = { parent: string | null; name: string };
const folders: Collection<Folder> = collection<Folder>("folders")
  .references(() => folders, "parent", { onDelete: "cascade" });

const remove = mutation("sessions.remove", { args: v.string() }, (ctx, id) => ctx.delete(sessions, id));

export default define({ collections: [orgs, sessions, events, folders], http: { "sessions.remove": remove } });
  • The check runs once the mutation’s code and its triggers are done, so the order of its writes doesn’t matter: write a parent and its children, or delete them, in either order.
  • It sees every row, whatever the access rules. Cascades act with the application’s rights, as triggers do, so they also delete rows the caller can’t see.
  • cascade and setNull are triggers on the target: the referring rows’ own triggers see the deletions and writes. They count toward the mutation’s budget and its 32 trigger rounds, so a chain of cascades is at most 31 deep, and deleting a row with many referrers in one mutation can run out of budget: delete them in pages first, as with any large deletion.
  • A reference held in fields gets an index of them, which finds a deleted row’s referrers; you needn’t declare it. cascade and setNull find rows by strings, numbers and booleans: a single field holding a whole tuple key is checked, but deleting its target fails with INVALID_REFERENCE rather than cascade.
  • Deploying a reference checks the rows already there: if one breaks it, the deployment fails with FOREIGN_KEY_VIOLATION naming that row, and the old code keeps serving. A staged deployment checks when it activates. References the old code already had aren’t checked again; removing one checks nothing.
  • List a collection that declares references in define({ collections }), or use it as a trigger’s or aggregate’s source: the SDK refuses to touch one whose references the server never received. Declarations without references don’t conflict with one that has them; two different sets do.
  • References hold within one database: in a partitioned application, rows refer to rows of their own partition.
  • Test databases check them as the server does.

Running totals

An aggregate keeps a per-group value, such as a sum, and updates it from each changed row. It doesn’t reread the whole group.

APIContract
aggregate(name, options): Aggregate<G, V>A derived value per group, where the group is a value of one index: the field’s type, or a tuple for several fields. Read it with ctx.get(agg, group). List it in definitions; its source collection is declared for you.
Aggregate<G, V>A Derived<G, V> with readonly aggregate: AggregateMetadata.
AggregateMetadataReadonly collection and fields, and version (a string) when the aggregate has one.
AggregateOptionsRequired source, index (a declared index name), initial(group), add(value, row, key, group) and remove(value, row, key, group). Keys are decoded for typed-key collections. Optional access, a DerivedAccess rule like derive’s, with the group as args: who may read a group’s value from a method. Aggregates fold every row, whoever may read it, so give one over a guarded collection a rule: access: ({ principal, args }) => args.eq(principal.claim("shop")). Optional version, a nonnegative integer or a string of 1 to 128 bytes: while it stays the same, deployments keep each group’s value instead of rebuilding it from all of its rows; change it whenever the callbacks (or what they call) would compute differently.
Maintain a sum from changed rows
import { aggregate, collection, define, query, v } from "@flower-js/sdk";

const lines = collection("lines", v.object({ shop: v.string(), cents: v.int() }))
  .index("byShop", ["shop"]);
const total = aggregate("shop.total", {
  source: lines, index: "byShop",
  initial: () => 0,
  add: (sum, row) => sum + row.cents,
  remove: (sum, row) => sum - row.cents,
});
const read = query("internal.shop.total", { args: v.string() }, (ctx, shop) => ctx.get(total, shop));

export default define({ definitions: [total], http: { "shop.total": read } });
  • add and remove must be deterministic, work in any order, and undo each other. Flower can’t check this for you.
  • Use integer units for exact totals. Floating-point sums can drift.
  • An update removes the old row and adds the new one, so moving a row between groups updates both.
  • Materialize an aggregate, or a value that reads it, to keep it maintained. Unmaterialized ones may rebuild on every read. Redeploying rebuilds them from all of their rows, in one evaluation, unless the aggregate has a version that didn’t change: give big ones a version.
  • If a reducer throws, the error is stored and the next relevant change rebuilds from scratch.
