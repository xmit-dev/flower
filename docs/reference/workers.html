External values

external from @flower-js/sdk keeps a result current for each input, computed by workers outside the database. The workers guide has a complete example.

APIContract
external(name, { input, result?, each?, lease? }): Externalinput(ctx, args) returns everything that affects the result, or null when there is nothing to compute. A result schema checks published values. With each, the arguments are that collection’s keys and pools can list or lease stale ones. lease: { defaultMs?, maxMs? } bounds lease lengths: 30,000 and 300,000 unless set. Add the value to define({ uses }).
External<A, I, R, Pool>A Derived<A, ExternalState<R> | null>: read it with ctx.get(value, args). Plus component, results (the stored results collection) and the methods below.
ExternalState<R>{ status: "pending" } or { status: "ready", value }. ctx.get returns null instead when there is no input.
ExternalWork<A, I>args, input, and key: the canonical JSON of both, which names this exact piece of work.
pending(ctx, args): ExternalWork | nullThe work for these arguments, or null when the stored result is current or there is no input.
publish(ctx, { args, key, value }): { accepted }Stores value only if key still names the current input. Racing workers keep the first result; stale ones get accepted: false.
next(ctx, { limit?, shard? }?): ExternalWork[]Pending work across the tracked collection, oldest first, leased or not. Needs each.
claim(ctx, owner, { limit?, leaseMs? }?): ExternalClaim[]Leases up to limit (16) keys that have waited longest, for leaseMs (lease.defaultMs). Other claims skip them until the lease ends. Longer than lease.maxMs fails with LEASE_TOO_LONG. Needs each, like the methods below.
renew(ctx, leases, { leaseMs? }?): (number | null)[]Extends each current lease and returns its new expiry, or null when the lease was lost: it ran out, was released, or the key’s input changed or was published.
release(ctx, lease, { delayMs? }?): booleanHands a leased key back, claimable again after delayMs (0). false when the lease was already lost.
ready(ctx): booleanA claim would find a key now.
stats(ctx): ExternalStatsThe claim backlog, like a queue’s stats.
http(prefix, { access? }?): ExternalHttpMethods to spread into define({ http }): `${prefix}.pending`, `${prefix}.publish` and, with each, `${prefix}.next`, .claim, .renew, .release, .ready and .stats. Over HTTP, claim takes { owner, limit?, leaseMs? }, renew takes { leases, leaseMs? } (at most 1,024), and release takes the lease plus delayMs?.
ExternalNextOptionsOptional limit (16; at most 1,024 over HTTP) and shard: [index, count], which keeps only keys whose hash falls in that shard. See sharding.
ExternalLease<A>{ args, key, owner, attempt }: one claim of one input. attempt counts claims of the current input, across owners, from 1.
ExternalClaim<A, I>An ExternalWork and its ExternalLease, plus expiresAt. Send HTTP methods the lease fields only.
ExternalClaimOptionsOptional limit (16; at most 1,024 over HTTP) and leaseMs.
ExternalStatsready, oldestReadyAt (when the longest-waiting claimable key became available) and nextAvailableAt (when a lease or retry delay next ends), or null.
ExternalHttp<Prefix, A, I, R, Pool>The types of the generated methods.
  • next finds a key only after its row in the each collection is written. An input that changes because of other records makes the value pending, and pending reports it, but next won’t list it until that row changes.
  • A write that leaves a tracked row without input also deletes its stored result.
  • If the input returns to an earlier value, the result stored for it counts again.
  • Leases spread work; they don’t guard results. publish accepts any result for the current input, leased or not, and ends the key’s lease.
  • A write that changes a leased key’s input voids the lease and any retry delay: the new input can be claimed at once.
  • A key whose lease ends goes back in line at its expiry time, behind keys that were already waiting.
  • The helper creates `${name}.input`, `${name}.results` and, with each, `${name}.stale`. Don’t reuse those names.

Worker loops

@flower-js/sdk/worker runs the loops that feed queues and external values. They use only the client, so they run in Node or a browser.

APIContract
runQueueWorker<P, R>(client, options): Promise<void>Runs jobs from a queue as a pool. One watch on `${queue}.ready` serves the whole process; once it fires, claims take jobs while there is room, runs work for each while renewing every held lease in one call, and completes or fails each job (or, with release, hands back those a drain cut short), retrying lost replies under one request ID. How many jobs run at once follows the backlog and the process’s load. Resolves once the signal aborts and held jobs finish. Rejects on errors that aren’t transient, such as a missing method.
QueueWorkerOptions<P, R>Required queue (the http() prefix), work(job, signal, control) and signal. Optional owner (a random ID; unique per process), concurrency ({ min: 1, max: 16 }), batch (1: jobs one claim may take, at most 64), claimers (4: claims in flight at once), wait (false: wait in the queue’s line), waitMs (60,000: how long a place in line lasts; an idle worker claims again at half of it), leaseMs (30,000), renew (true; needs the renew method), marginMs (a fifth of leaseMs), drainMs (once stopping, how long held jobs may run before their signal aborts and they fail; work still running 5 s after that is given up on, with an unreported event, and runs again once its lease ends; by default they run to the end), release (false; needs drainMs and the release method: jobs still running when it ends go back to the queue with no error, to run again at once), scope (for scope: "argument"), retry, health (processHealth()), adjustEveryMs (250) and onEvent.
QueueWorkerControlThe third argument of work. throttle(ms, reason): the service behind this job refused it for being asked too much, so the worker claims nothing for ms and, unless concurrency is a number, halves how many jobs it runs at once. idle(): from now on the job mostly waits, on a child process or a server say, so it stops counting toward concurrency and long jobs can’t keep out short ones.
QueueWorkerEventclaimed (with job), completed, failed (with error), released (handed back when drainMs ended), lost (the lease ended first), unreported (the outcome couldn’t be sent in time), limit (with the new limit and its reason) and waiting (Flower is unreachable).
Concurrency, AdaptiveA number fixes how many jobs run at once. { min?, max?, initial? } (1, 16 or min if larger, and min) lets it adapt within bounds.
processHealth({ busy?, memory? }?): HealthReads this process’s load: how busy its event loop was since the last read, over busy (0.9), or how full its heap or memory is, over memory (0.85), whichever is higher. Work in child processes or on other machines doesn’t count. In a browser, which exposes neither, it reports idle.
Health, Load, HealthLimitsHealth is () => Load, called at every adjustment. A Load is { load, reason }: 1 where the process falls behind, and what loads it most, such as "event loop 97% busy". HealthLimits are processHealth’s options.
reconcile<A, I, R>(client, options): Promise<void>Waits for pending work, runs compute, and publishes the result with its key. Stale results are rejected, never stored. Resolves once the signal aborts.
ReconcileOptions<A, I, R>Required external (the http() prefix), compute(input, work, signal) and signal. Optional args (keep one key current; omit to drain every stale key through next), shard, lease (claim keys instead of listing them; not with args or shard), concurrency (1; at most 1,024 with lease), batch (16), retry and onEvent. With lease only: owner (a random ID), leaseMs (30,000), marginMs (a fifth of leaseMs), and concurrency as bounds { min, max, initial }, which grow the number of computations while keys wait and cut it once the process falls behind, as runQueueWorker does, with health (processHealth()) and adjustEveryMs (250).
ReconcileEventpublished (with key and accepted), failed (with key and error) and waiting. With lease, also claimed (with key and attempt), lost (with key: the lease ended before a result) and, with adaptive concurrency, limit (with the new limit and its reason).
  • The generic parameters type job.payload, results, arguments and inputs; they aren’t inferred from the app.
  • An adaptive limit works like a TCP congestion window. While claims come back full and the pool is full, the limit doubles each adjustment when the process is under half its load, and grows by a sixteenth when it is busier or was recently cut. When the load reaches 1 it shrinks by a quarter, at most once a second. A full pool keeps its readiness watch open, so it still sees work waiting when long jobs hold every slot.
  • After the watch fires, one claim asks at a time until claims come back full, so a single new job costs one claim rather than one per claimer. With batch above 1, the claims send max. Several claims that take many jobs beat many that take one: claims of one queue conflict with each other.
  • With wait, the worker claims with max and waitMs and watches ready with its owner, so a new job wakes the process first in line instead of every idle one. It needs the claim and ready methods queue.http() generates. On the way out it leaves the line.
  • work can run again after a crash: give external services job.id as an idempotency key. Its signal aborts marginMs before the lease would end.
  • A work error fails the job with { message }, and the queue’s retry policy decides what happens next.
  • compute may run more than once for the same input. Failures back off per key.
  • With lease, a pool claims at most one key per free computation and renews all of its leases in one call, every third of leaseMs − marginMs. compute’s signal aborts when a lease is lost or is about to end. A failed key is released with a backoff every pool honors; a stopping pool releases its keys at once.
