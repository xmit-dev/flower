# Where Flower scales, and what still couples work

Flower is unreleased. This describes the current implementation and its limits. Measured capacity belongs in [READS.md](READS.md); [the benchmark guide](README.md) defines the workload and accounting. None of the mechanisms below implies a particular throughput.

## Writers, placement, and durability

Each physical Raft group has one ordered durable log. Named logical partitions have independent application writer queues and revisions; groups spread their consensus and storage work. Placement is catalogued and epoch-fenced. Operator resize plans move complete partitions and balance partition counts; they do not provision servers or automatically optimize placement by measured load.

A writer batches ordered calls and overlaps preparation with its predecessor's commit. It can prepare a bounded wave of mutation candidates concurrently against an immutable base. Each candidate carries native dependency stamps. Before accepting it, the ordered sequencer rechecks its reads, missing keys, index membership, derived outcomes, write bases, graph shape, code, authorization principal and policy, retry identity, capacity, and prepared-transaction locks. Invalid candidates are recomputed; speculative entropy and results never escape before commitment. Conflict feedback narrows the next wave. Local unapplied-log and voting-quorum replication backlogs suspend successor preparation above the normal one-group overlap, preserving batch amortization while outstanding work drains. Learners and a lone slow voter do not impose this gate; joint membership requires each majority. Remote application lag is not inferred from replication acknowledgments. `FLOWER_WRITER_PREPARATION_WORKERS=1` selects serial preparation.

Parallelism helps independent work. The pizza workload concentrates writes on hot stores, which can invalidate speculative candidates. A shared materialized leaderboard also deliberately couples its inputs. Additional callback threads cannot remove these dependencies, a leader's ordered log, or a shared disk's flush latency.

Already queued public mutations in a serial stretch share one blocking worker dispatch, including the adaptive policy's cooldown after conflicts. They still execute separately and in order, with a fresh callback heap, clock sample, guards, rollback boundary and receipt for each call. The same staging path checks byte/time limits between calls and leaves a refused suffix queued. Authorization hooks and deployments keep their ordinary paths. Canceling preparation wakes pending evaluation waits and stops after an in-flight callback finishes; preparing a successor does not delay the predecessor's durable acknowledgements.

Prepared patches share immutable JSON allocations with the writer's private snapshot until batch compaction. A vector preserves the incoming patch's sorted unique keys without constructing another search tree for each invocation; final compaction still uses an ordered map. Overwritten intermediate values are discarded without a staging copy; only final surviving values need owned JSON for the existing Raft format. A final value still held by a successor snapshot requires one copy, so unique-key workloads benefit less. Each invocation keeps its own receipt and revision, and both the original per-command byte admission and final scoped-command size checks still apply.

Adaptive sizing uses learned preparation and durability costs. Healthy queues use partial-backlog batches; once the oldest call cannot meet the soft age preference even with one durability round, recovery targets the queued work within the configured preparation, count, and maintenance bounds. Near a maintenance boundary, the writer drains its prepared group instead of starting another small durable group. A successor keeps accepting arrivals until its predecessor completes, since it cannot be submitted sooner; the adaptive targets bound it only afterwards. An explicit pending-maintenance flag makes that yield effective even with saturated customer queues. The default 50 ms preparation ceiling is checked between callbacks; it is neither a response deadline nor a preemptive timer guarantee.

Durable acknowledgements rely on quorum-durable Raft log entries plus local atomic application. Records, retry receipts, revision, membership, and the applied log position publish together in memory; one background task then writes each applied state, in order, as a redb transaction with deferred durability, coalescing states that queued while the disk was busy. Neither Raft nor readers wait for that write. Subsequent Immediate log, vote, snapshot, or purge transactions also persist prior writes; application performs no fsync of its own. Snapshot checkpoints, purges and installations first drain the queue, so Raft never prunes a log entry whose state is unwritten. Snapshot checkpoints flush the existing application tables and record metadata only; they do not persist a second full state image. Installation and log retention remain durable. This uses the existing redb Raft log and transaction engine, not a new WAL or general background checkpoint scheduler.

A leader of at least three voters does not wait for its own log flush. Flower's vendored OpenRaft 0.9.25 ([vendor/openraft/FLOWER.md](../vendor/openraft/FLOWER.md)) replicates a leader's entries as soon as storage can read them, and counts the leader toward the commit quorum only after its flush callback. Followers alone form a majority, so the leader commits its appends without an fsync and completes their callbacks from one Immediate commit when an entry stays uncommitted for 30 ms (for example, a follower is down) and otherwise at most every 500 ms. A crashed leader can lose only its unflushed tail, which a majority still holds. It returns as a follower: opening its store reloads its own committed vote as uncommitted, so it must win a later term, which its shorter log cannot, rather than resume its own and append under log ids the majority already holds. `FLOWER_LEADER_FLUSH=immediate` restores flushing every append; `FLOWER_LEADER_FLUSH_GRACE_MS` and `FLOWER_LEADER_FLUSH_INTERVAL_MS` tune the two bounds.

Raft command decoding uses one field-presence scan to skip impossible wrapper variants, preserving their original precedence and malformed-wrapper fallbacks. Scoped payloads borrow the existing JSON buffer and reuse that scan instead of copying into an intermediate map and another command buffer. The selected typed decoder still validates the complete command and each record's independent depth budget; this does not change the wire format or durable log contents.

If startup finds durable logs beyond the recovered applied position, all logical partitions on that node share a serving barrier until a quorum-confirmed fence has been applied locally. Replica-local reads can therefore need quorum during startup recovery; after recovery they retain their normal lag-tolerant semantics. Only confirmed committed work is replayed, never every durable tail entry. Peer traffic and diagnostics remain available while the barrier is pending. Forward metadata migration retires the old format, and an updated compatibility contract rejects mixed older/current nodes and unsafe directory downgrades.

## Incremental data and dependency validity

[Ordered tuple indexes](../INDEXES.md) support prefix/range bounds, bounded pages, forward/reverse order and continuation. Timers, TTL sweeps and work queues use these primitives from TypeScript. Native index maintenance costs writes, but selecting one due job no longer sorts its whole collection. Pages continue on each invocation's selected snapshot; they are not a pinned multi-page snapshot.

The graph's structure is durable. Each stored cell has a `reader:` record per dependency, so a change finds its readers by prefix, and a `height:` record when it reads other cells. Loading or restarting rebuilds none of it. A preview recomputes heights only for cells whose derived edges changed, propagating through their readers: a cycle drives heights past the 128 limit. Cells that lose their last reader or root are collected with their own records, so removals and changed edges need no traversal of the whole graph. Deployments, which reevaluate every cell, and a callback error that retains unevaluated dirty children still traverse from every root. Unchanged intermediate outcomes can stop downstream propagation; multi-branch cases remain conservative to preserve evaluation semantics. Randomized reference comparisons cover state, patches, outcomes, dependencies and rollback, rather than requiring an optimization to execute unnecessary callbacks.

Final graph validation can discard its private overlay on failure, so it avoids the rollback snapshot needed by intermediate previews that application code can catch. Patch finalization releases overlay references before moving uniquely owned JSON trees into the result; values still shared with older snapshots use the copy fallback. Rust key encoding appends strings directly when they need no escaping and counts UTF-8 bytes plus required escapes without decoding every character. Exact output budgets and key identity remain unchanged.

Read results carry the same kind of native dependency certificate. After any required read fence and current authorization, a cache entry can survive unrelated commits. Missing-key and index-membership stamps cover phantom inserts. Clock-sensitive and managed-crypto-dependent queries conservatively bypass reuse. Cache and in-flight metadata have explicit byte budgets; zero disables them. Fresh reads still pay for a quorum-backed fence, and replica-local reads may lag.

SSE hubs share eligible query evaluation, immutable snapshots and encoded diffs across subscribers with the same invocation, full principal, deployment and consistency policy. Each subscriber still authorizes independently, including when only credential expiry changes. A fresh join establishes a new fence. Slow consumers receive a full reset or disconnect; they cannot silently miss a patch base. Watches may coalesce intermediate revisions and are not durable event logs.

## Resource boundaries and authorization

Heavy preparation admission is node-wide across logical partitions, with separate ordinary and reserved control capacity. Fair partition lanes bound queued input bytes and active work under `FLOWER_PREPARATION_WORKERS` and memory reservations. Permits follow blocking evaluation after caller cancellation; retained output has its own lifetime. More HTTP/2 streams do not create more evaluation capacity.

Public HTTP queries can validate an encoded cache hit without taking a heavy preparation slot. Input/key scratch and response bytes use the shared user byte budget; concurrent probes use `FLOWER_QUERY_WORKERS`, shared with authorization callbacks. Probes never queue for that semaphore. A miss or busy probe releases its temporary snapshot and reservations, then enters ordinary fair admission and captures a new snapshot. Freshness fences, current alias/policy checks, partition gates, transaction locks and dependency validation still apply. Queries in applications with authorization hooks or managed keys keep the full admitted path, as do SSE refreshes. This best-effort probe path has no separate fairness guarantee. The HTTP body owns its byte lease through transport, without retaining a database root or evaluation slot. Inspect authenticated `/admin/resources` and the [budget reference](LIMITS.md) when tuning; lookup leases count toward retained bytes, not active preparation slots.

QuickJS starts every callback from the same pristine logical state, backed by reused compiled modules, pools and base/static application images. Before capturing an image, the host collects unreachable cycles and resets QuickJS’s normal 50% allocation headroom. Trusted initialization creates frozen method and derived contexts before application initialization and publishes them, so the SDK binds its typed contexts into the snapshot instead of in every callback. Each image reserves a 4 KiB input buffer; small invocations avoid the guest allocator, and larger invocations allocate normally. Automatic GC and execution/memory budgets remain enabled.

Finished instances return to one process-wide pool per image, shared by every thread. A background thread, `flower-wasm-reset`, restores their linear-memory bytes and every mutable numeric Wasm global off the request path; a caller that finds only unrestored instances of its image resets one itself instead of instantiating. Host callbacks, entropy permissions, authorization/key caches and memory accounting are replaced for the next invocation. Nested callbacks check out distinct active instances. Traps, execution failures and memory growth discard instances; business-error envelopes can reuse storage after the same complete reset. A module-level validator rejects hidden globals, mutable tables, segment-use/drop operations, reference state and unsupported Wasm proposals. Immutable function tables can remain in the same instance. Idle instances are released after 30 seconds, when another image needs their budget, or when Wasmtime runs out of instance slots.

Values cross the guest boundary in a binary encoding ([GUEST_ABI.md](../GUEST_ABI.md)): tagged little-endian fields, strings in QuickJS’s stored Latin-1 or UTF-16 form, and map keys interned per message. The guest reads object shapes, arrays and string buffers directly, without running application getters or `toJSON` hooks, and decodes host replies into arrays allocated at their final length. The same ABI runs deployed WebAssembly guests, whose bundles carry a module instead of JavaScript.

On Linux and macOS, exact write tracking avoids copying untouched pages. Protected pages are unchanged; hot pages stay writable, and every reset copies them from the immutable snapshot. On Linux 6.7+ where the process may create a user-mode userfaultfd, asynchronous write protection lets the kernel record writes, including host and system-call writes, without signals: each reset scans and re-protects exactly the pages written since the previous one, and only a page written in two resets within four stays hot. Otherwise, or with `FLOWER_WASM_DIRTY_PAGES=signal`, a first write to a protected page faults once and makes that OS page hot, and Rust writes mark their complete spans explicitly, including nested callback inputs and crypto output. A signal-tracked hot set that outgrows twice its expected size plus 256 KiB is protected again, and every 1,024 resets either tracker protects all pages again, so one unusual callback cannot inflate every later reset. A new instance starts with its image's learned seed hot: the pages written by both of the image's two most recent exact single-callback footprints. This uses no hashes, sampled comparisons or predicted write ranges. Growth and destruction remove protection before mappings change or return to Wasmtime. Other platforms and `FLOWER_WASM_DIRTY_PAGES=0` use full-memory copies; `FLOWER_WASM_RECYCLE=0` uses new instances for every callback. macOS uses Wasmtime’s Unix signal handling instead of Mach ports for this tracker. Idle storage consumes up to `FLOWER_WASM_RECYCLE_BYTES` (96 MiB by default) and half the configured instance slots per process. Zero or an image larger than the byte allowance bypasses reset-snapshot capture, tracking setup and retention, using a fresh copy-on-write instance; see the [budget and capacity tradeoffs](LIMITS.md).

The underlying Wasmtime pool keeps each 4,096-entry function table allocation resident and clears it when creating another instance, trading up to 32 KiB per pooled table on 64-bit hosts for fewer operating-system remaps. Resident reuse keeps only the same instance’s immutable function mapping; a newly created instance still receives its own table and copy-on-write memory image. A 4 GiB virtual address reservation on 64-bit hosts lets generated code use guard pages for ordinary memory accesses; it does not commit that memory or raise the operator's guest-memory limit. The guest is compiled with standard WebAssembly SIMD so string scans and copies can be vectorized, with no relaxed SIMD or fast-math.

The SDK's canonical key encoder delegates finite JSON scalars and ordinary dense arrays of scalars to a protected native QuickJS helper. It uses the engine's own string escaping and number formatting, and checks that the relevant intrinsics remain unchanged. Unsupported shapes, proxies, accessors, nested values and modified intrinsics fall back before running application code. The same TypeScript implementation remains available in other JavaScript hosts; this does not expand database values beyond finite JSON. Native host replies also serialize their fixed success envelope directly, avoiding a temporary JSON map.

Eligible host calls parse reply bytes directly in QuickJS instead of constructing a temporary JavaScript string. Intrinsic and shape guards retain the ordinary JavaScript path when its observable behavior could differ. A callback's final serialized result retains QuickJS's string buffer until the Store is dropped or its heap is restored, avoiding another guest allocation and copy. Setup operations retain their ordinary owned-buffer lifecycle; the host copies or decodes results before either operation.

Application authorization is a pure deployed hook that receives credentials separately from business arguments. It runs before receipt replay, query-cache use and watch delivery, and returns the principal available through `ctx.principal()`. Named partitions verify its tenant binding. Receipt ownership uses stable identity; cache sharing uses the full principal. Untrusted tenant strings alone do not establish identity. The demo remains an unauthenticated benchmark application unless an authorization hook is added.

TLS can authenticate server identities and encrypt client/peer links. A distinct peer credential separates peer RPC access from the operator token. Replicas remain trusted, not Byzantine-tolerant, and a peer credential is not a limited application capability. See [TLS.md](../TLS.md).

## Transactions and movement

[Distributed transactions](../TRANSACTIONS.md) target physical groups or movable logical partitions. Different request IDs can coordinate independently. A prepared participant locks its targeted logical partition, or the default namespace for a physical-group call. Co-located unrelated named partitions continue serving. Conflicting intents abort rather than acquiring locks in an indefinite cycle; a durable prepared intent cannot be released merely because a timeout elapsed.

Movement pins placement epochs, waits for active transactions to finish, checks destination key readiness and transfers retry/protocol state. Pre-copy captures a durable immutable base while the source keeps serving. A brief freeze produces and transfers a final delta, then performs epoch-fenced cutover. A large delta can fall back to a full frozen image. Captured bases and copy phases survive restart; this is additional disk/state cost while a move is active. Encoding acquires reserved node-wide Control capacity before pinning source roots. A byte lease follows each cached image, and difference construction reserves workspace before allocation; insufficient shared capacity can delay a frozen move. See [the field guide](../docs/operate/#resizing).

Ordinary atomic tenant work should stay local. External effects belong in an outbox plus workers, with downstream idempotency and fencing. A lease cannot prevent a paused worker from later contacting a different service. `ctx.history()` and lease history identity expose restore fencing to application code, but the downstream system must enforce the accepted history and token.

Durable staged deployment backfills added index definitions in bounded native pages while old code and authorization keep serving. Source writes maintain both active and proposed indexes. Activation atomically switches code, policy and schema; cancellation and incremental cleanup preserve active/shared indexes. Materialized roots rebuild in adaptive pages into a hidden generation, with completed roots maintained by source mutations and an atomic active-graph switch. Each page computes the heights of the cells it adds from their children's stored heights, and removals collect only what they release. One root dependency closure, graph metadata, and clock/key refresh still obey evaluation budgets. Target maintenance bypasses speculative preparation while retaining serial batching and grouped commits; progress alone preserves query cache validity. Fatal target-maintenance failure fences the build while preserving active writes. Arbitrary application migrations require explicit application progress. See [the staged lifecycle](../INDEXES.md#resumable-staged-deployment) and [its scaling benchmark](STAGED_DEPLOYMENT.md).

## Growth limits and measurements still needed

Each replica serves application state from redb read snapshots. Memory holds the writes still queued for disk, a bounded cache of parsed values, redb's page cache and the scan windows that span values of their first index field ([FOOTPRINT.md](FOOTPRINT.md#serving-from-redb)). Raft snapshots capture immutable roots and durably checkpoint redb metadata, fencing publication against a newer install. Full JSON transfer images are encoded lazily on the first read and stream to the peer as they encode; they are not stored in redb or in a temporary file. Local recovery serves the application tables and regenerates transfer images from that durable state. Installing a received image appends its records, in key order, to a temporary spool file as it decodes, then copies them into the application tables, so neither side holds the image in memory. Entry-count snapshot triggering is supplemented by applied-log bytes and nonidle age, with measured build-cost cooldown for the soft triggers. Age restarts at process startup; byte accounting recovers from durable log positions. Count/manual triggers can bypass cooldown. This removes a long critical section and a full in-memory wire buffer. Migration bases and live reader roots also consume resources.

[Retry retention](../RETENTION.md) is opt-in and explicit. Epoch floors and acknowledged/closed sessions reject old IDs before receipts are collected. Uninitialized legacy databases keep their old indefinite retry contract. Restore requires a new incarnation and external fencing, not a clock-based assumption that the old cluster stopped. Transaction closure has a separate delayed-message protocol; ordinary receipt deletion is not sufficient.

The hot pizza workload retains only 96 orders per group. It does not establish performance for millions of keys, broad distinct queries, long-lived snapshots, large deployment backfills, many watch scopes, crypto-heavy traffic, or cross-partition transactions. Measure those independently before selecting disk-backed application MVCC, finer transaction locks, or a more extensive background checkpoint engine. The [design review](../DESIGN.md) records the boundary between implemented changes and those larger experiments.

Use both closed-loop and independent offered-load measurements, with durable mutation goodput, tails, rejections/driver drops, queue age, timer lateness, retained bytes, recovery and independent audits. Keep callback isolation, fresh-read semantics and durable acknowledgements intact when comparing configurations.
