# Flower protocol and state format

## Public data API

All external data access invokes deployed TypeScript methods. JSON values must be finite and serializable; records use collection names and string primary keys, and the SDK stores typed JSON keys as their canonical JSON text. Objects with prototype-like keys are supported safely.

The deployed bundle's `http` table is the complete allowlist. Request names are public aliases, resolved to internal definitions from the allowlist captured with the application state. Unlisted or removed aliases return `404 METHOD_NOT_FOUND`, including retries of previously committed requests.

`POST /v1/call` accepts `{name, args?, requestId?, expectedRevision?, credentials?}` and returns `{revision, value, duplicate}`. The deployed allowlist determines the invocation kind. Mutations require `requestId`; queries ignore it and reject `expectedRevision`. Queries always return `duplicate: false`.

`POST /v1/query` accepts `{name, args?, credentials?}` and additionally requires an exposed query method. Evaluation reads one captured snapshot under the deployed method’s fresh or explicitly replica-local policy and produces no durable changes. Reads of unmaterialized derived values are temporary.

`POST /v1/mutate` accepts `{name, args?, requestId, expectedRevision?, credentials?}` and additionally requires an exposed mutation or transaction method. Source changes are produced by method code through its context, never by raw operations from the request. The return value and final materialized graph commit atomically. Both kind-specific routes return the same result shape as `/v1/call`; a kind mismatch returns `422 METHOD_KIND_MISMATCH`.

Optional credentials travel outside business arguments and retry fingerprints. A deployed pure authorization hook produces an immutable principal `{subject, tenant?, claims?}` before receipt replay, query-cache reuse and watch delivery; on a named partition the principal's tenant must equal the partition name. The SDK compiles the hook from `define({ auth })` and per-method `access`: it admits anonymous callers as subject `$anonymous` (with the partition as tenant on a named partition), which methods observe as `ctx.principal() === null`. Missing hooks preserve anonymous application access with a null principal. The SDK's hook also reports what deciding read of the call's arguments (nothing, or top-level fields by name); the service reuses a decision for the same credentials, method, partition and delegation with arguments that agree on those fields (equal arguments, when it read more of them, including arguments that are not an object, or when the hook reports nothing), while the records it read are unchanged and its declared time has not come (a JWT's expiry, for instance), so the hook runs about once per credential and method rather than once per request. Such a reused decision skips the hook's check of the arguments against the method's schema; the method checks them again (`422` `INVALID_ARGUMENT` rather than `403`). Current authorization requires a fresh snapshot even when the method declares replica-local reads, so protected reads and watches still need quorum. Declared managed keys impose the same fresh-policy requirement.

Unknown request fields are rejected. Raw record reads, transaction patches, database snapshots, and database changefeeds are not public endpoints. Watches expose only a deployed query method’s returned value.

## Errors

Every error response has a JSON body:

```json
{"error":{"code":"EVALUATION_FAILED","failure":{"code":"OUT_OF_STOCK","details":{"available":1,"item":"dough"},"message":"Not enough stock"},"message":"OUT_OF_STOCK: Not enough stock"}}
```

`error.code` names the server outcome and `error.message` is diagnostic text. `error.failure` appears only when application code or the evaluator produced the error, as `{code, message, details?}`. Object keys carry no meaning in their order.

| Status and `error.code` | `error.failure` |
| --- | --- |
| `422 EVALUATION_FAILED` | The method's failure. A thrown exception's string `code` property becomes `failure.code` (`COMPUTE_ERROR` when absent; exhausted execution or memory budgets report `EVALUATION_BUDGET`), its message `failure.message`, and a JSON `details` property `failure.details`. `error.message` is `CODE: message`. A few server-side evaluation errors, such as a transaction planner that writes, omit `failure`. |
| `403 FORBIDDEN` | The authorization hook's failure when the hook threw, for example `UNAUTHENTICATED`, `FORBIDDEN` or `INVALID_ARGUMENT` from the SDK; `error.message` is then `Authorization denied`. Server-side denials, such as a principal outside a named partition's tenant or an invalid principal, omit it. |
| `422 TRANSACTION_ABORTED` | The failing participant method's failure. The durable coordinator record stores it, so retries with the same request ID return it again. Aborts from conflicts, unavailable or uncertain participants, or coordinator recovery omit it. `error.message` is the abort reason. |

Other errors carry no `failure`, for example `400 INPUT_INVALID`, `404 METHOD_NOT_FOUND`, `409 REQUEST_ID_REUSED`, `422 METHOD_KIND_MISMATCH` and `503 UNAVAILABLE`. Details survive only for methods, including the authorization hook and transaction planners: derived outcomes store `{code, message}`, so a method that reads a failed derived value reports its code and message without details. Details that are not JSON are dropped. The SDK's `fail(code, message, details?)` requires UPPER_SNAKE_CASE codes and JSON details; other throwers can use any string. Forwarding to the leader preserves the status and body, including `failure`. The SDK throws `FlowerError` with `status`, `code`, `message` and `failure`; `isTransient` never retries an error that has a `failure`.

## Query watches

`POST /v1/watch` accepts `{name, args?, credentials?}` and requires a currently exposed query method, with the same JSON validation and kind errors as `/v1/query`. Set `Accept: text/event-stream`; success is an SSE response with `Content-Type: text/event-stream`. Errors detected before streaming use ordinary JSON HTTP error responses.

Data events are:

```text
event: snapshot
id: 0
data: {"sequence":0,"revision":12,"value":{"items":[]}}

event: patch
id: 1
data: {"sequence":1,"baseSequence":0,"revision":14,"patch":[{"op":"add","path":"/items/0","value":"pizza"}]}
```

A patch contains RFC 6902 `add`, `remove`, or `replace` operations. JSON Pointer path segments escape `~` as `~0` and `/` as `~1`; an empty path addresses the whole value. A later `snapshot` replaces the value when a patch would be larger or its diff budget is exceeded. Its sequence continues increasing. Sequence and `baseSequence` describe a shared producer’s values, independently of application revisions. The first snapshot may use any nonnegative safe-integer sequence. Later snapshots must increase the sequence but may skip numbers to reset a lagging consumer. Patches require `sequence = previousSequence + 1` and `baseSequence = previousSequence`; applying a patch across a gap is a protocol error. Identical values produce no data event even if the revision advanced. Changed clock-dependent values can share a revision.

Watches have no periodic tick. A commit wakes a watch only when it wrote something that watch's current result read, as the result's dependency certificate records it (records, missing keys, collection and index membership, index windows, derived outcomes), or something its subscriber's authorization read. Writes of code, policy or configuration wake every watch. A result with no certificate, because it read `ctx.now()`, its logical database holds a materialized value that reads the clock, or its reads outgrew the certificate budget, wakes on every commit of its logical database; so does a subscriber whose authorization has none. Resolving a managed key directly keeps the certificate: key catalog writes, like code and policy, wake every watch. A result that reads `ctx.clock()` keeps its certificate, since it declares when time changes it. Each node also condenses Raft metrics into two events that wake every watch: the replica stopped, or its freshness became suspect because its role, term or leader changed or, as leader, its lease (`election_timeout_max` from the send time of the last quorum-acknowledged heartbeat) lapsed. Time wakes a watch only at the instant its evaluation declared with `ctx.changesAt()`, either in the query or in `authenticate`; JWT verification and decryption declare a token's expiry or activation themselves. A result or authorization that reads `ctx.now()`, or fails to decrypt a JWT, promises nothing about when it changes, so its watch is re-evaluated every `FLOWER_WATCH_REFRESH_MS` (250 ms by default). A named partition's watches also wake when its owner's claim lapses: while any watch is open, one monitor per partition renews the cached route exactly as it expires (`FLOWER_ROUTE_CACHE_MS`) and wakes them if the partition moved or the catalog could not confirm it. An idle fresh watch therefore re-proves quorum only after one of those events: a replica cut off from its leader notices within Raft's election timeout, and an isolated leader within its lease. A follower that keeps hearing a leader which has itself lost quorum, possible only with five or more voters, keeps its last values until it hears the new term or a write. Every subscriber enters node admission before taking a snapshot, resolves the current allowlist, obtains its declared fresh/replica-local read fence, and runs its own authorization. Subscribers with identical invocation, complete admitted principal, deployment and consistency share one producer per logical database on this process. The producer evaluates and diffs once, and shares immutable encoded buffers; credentials remain subscriber-local. A new subscriber obtains its own read fence and, for clock-dependent results, a fresh evaluation. Deployment or admitted-principal changes terminate the old scope with `WATCH_SCOPE_CHANGED`; expired/revoked credentials fail their own authorization even if another subscriber still has access.

Intermediate commits can be coalesced. If a subscriber skips a producer update, the server sends a complete reset snapshot rather than an invalid delta. An output channel holds one event. Updates send immediately when space is available; when a changed update finds the queue full, the subscriber discards its unsent update and waits for space, batching intermediate changes into one refresh of the latest value. That refresh reacquires admission, the declared read fence and current authorization before sending. If room to send that update remains unavailable for five seconds by default, the subscriber closes with a terminal slow-consumer error. Snapshot/patch data and subscriber input retention consume the node’s configured byte budget; there is no subscription-count ceiling. Normal evaluation budgets and bounded diff work still apply. Periodic SSE comments may keep an unchanged connection alive and do not advance its sequence. This is a live value subscription, not retained event history.

After streaming starts, a terminal error is emitted as one `event: error`, without an `id`, whose data is the JSON error body plus the HTTP status the error would have had; then the connection closes:

```text
event: error
data: {"error":{"code":"EVALUATION_FAILED","failure":{"code":"EMPTY","details":{"item":"dough"},"message":"Out of stock"},"message":"EMPTY: Out of stock","status":422}}
```

`failure` follows the rules for HTTP errors: it is present when the watched query fails (`422 EVALUATION_FAILED`) or the authorization hook rejects a refresh (`403 FORBIDDEN`). Other terminal codes include `503 WATCH_SCOPE_CHANGED`, `503 UNAVAILABLE` and `408 WATCH_SLOW_CONSUMER`. Errors detected before the first snapshot, including a query that fails on its first evaluation, are ordinary JSON responses with that status. Abrupt transport loss may close without an error event. Cancelling the client body releases its watch resources.

A new connection always starts with a full `snapshot` at its producer’s current sequence, which need not be zero. `Last-Event-ID` is not a resumable cursor and is ignored; the server retains no watch history. The SDK turns an `error` event into `FlowerError` with its `status`, `code` and `failure`. `watchDeltas` yields typed wire events and `watch` applies patches and yields isolated `{revision,value}` results; neither reconnects. `subscribe` reconnects after disconnects, stalls without bytes (heartbeat comments count) and transient errors, including `WATCH_SCOPE_CHANGED`, `UNAVAILABLE` and `WATCH_SLOW_CONSUMER`, and flags the first value of each connection as `reset`; any error with a `failure`, and any other 4xx except 408, 425 and 429, ends it. Abort and iterator return close the request, including return during a pending read. `watchPoll` remains the explicit polling alternative. The SSE parser bounds each event to 17 MiB and reconstructed JSON values to 16 MiB.

## Privileged operations

`POST /admin/deploy` accepts `{requestId, bundle: {hash, javascript}, preparation?: "online" | "blocking"}`. Online is the default: preparation runs against an immutable base while old code serves, then atomic cutover publishes it from the writer lane. If writes committed meanwhile, cutover evaluates the bundle again on the current revision, as blocking preparation does, provided the online evaluation took at most `FLOWER_DEPLOYMENT_CUTOVER_MS` and its compiled image is still cached; the repeat must also finish within that time. Otherwise a changed base returns `409 DEPLOYMENT_CONFLICT`; retry the same request ID, optionally selecting blocking preparation. Strategy does not change retry identity. Bundle hashes are lowercase SHA-256 digests. JavaScript is a bundled IIFE exposing `__flowerBundle.default`, the manifest returned by the SDK's `define()`. When it begins with `/* flower:static-init */`, the SDK default, module initialization runs once per prepared image; otherwise it reruns in every callback. `definitions` maps internal names to descriptors; `http` maps public aliases to `{name: internalName, kind: 'query' | 'mutation' | 'transaction', consistency?: 'replica-local'}`. `maintenance` is `null` or `{name: internalName, kind: 'mutation', onError?: {name: internalName, kind: 'mutation'}}`; the SDK registers `$flower.maintenance` and `$flower.maintenance.error` there when the application has any task. Optional `authorize: {name}` names the private authorization query, `$flower.authorize` in SDK bundles. Optional `collections` lists `{name, indexes}` declarations and optional `keys` lists managed-key declarations. Deployment validates every method reference and kind, then commits the registrations with the bundle and recomputed graph. A failed deployment activates neither code nor registrations. Old bundles using a flat default export must be rebuilt with the new manifest. Structured manifests without maintenance or without an error handler remain valid.

Deployment and operator initialization/membership/metrics routes require `FLOWER_ADMIN_TOKEN`. Internal Raft, forwarding, partition and transaction RPCs require `FLOWER_PEER_TOKEN`; omission defaults to the operator token for local experiments. Initialize accepts a map of distinct node IDs to distinct `host:port` addresses. Peer RPCs include `x-flower-target-node-id`; the server rejects a different target before processing. Responses include `x-flower-node-id`, which the sender verifies before accepting the RPC. This prevents address aliases from counting one process as several voters. `/health` is public and contains no database state. Configure native TLS for encrypted traffic outside a trusted cleartext network.

## Retry and lifecycle metadata

| Endpoint | Authorization and input |
| --- | --- |
| `POST /v1/identity` | Public fresh metadata only; returns `{revision,value}` with null or `{database,incarnation,currentEpoch,minEpoch}`. |
| `POST /v1/session` | Current application hook required. `{operation:"open"|"status"|"ack"|"close",session,incarnation,epoch?,through?,limit?,abandon?,credentials?}`; fields depend on operation. Ownership is derived from principal, never accepted from JSON. |
| `POST /admin/retention` | Operator token. `{operation:"status"}` or `{expected_revision,action}` with initialize/advance/collect/set_budget/reincarnate. |
| `POST /admin/deployments` | Operator token. `{operation:"stage",requestId,bundle}`, `{operation:"status"}`, `{operation:"advance"|"collect",requestId,maxBytes?}` or `{operation:"activate"|"cancel",requestId}`. Durable staged index and materialized-graph build, explicit bounded progress, and atomic cutover. |
| `POST /admin/transactions` | Operator token. `{operation:"status"}`, `{operation:"close",through?,maxBytes?}` or `{operation:"collect",maxBytes?}`. Reports durable closure state and bounded partial progress; success alone does not assert completion. |
| `POST /admin/keys` | Operator token. Metadata and encrypted native key lifecycle operations; [SECRETS.md](SECRETS.md) defines their full schemas. |
| `GET /admin/resources` | Operator token. Node-local admission accounting plus snapshot policy/byte/age/duty metrics, not database data or a logical-partition routing operation. |

All POST routes in this table also work below a named-partition URL. In the SDK, `FlowerAdmin` wraps the operator routes and `FlowerClient` the identity and session routes. `f1` epoch IDs and `f2` session/sequence IDs bind a logical history; native application rejects retired identities before receipt lookup. Initializing retention rejects legacy IDs even if a stored receipt remains. Physical collection is incremental and preserves rejection floors. Distributed closure separately obtains participant floors before collecting protocol detail; admissible aborts and incomplete work block a prefix. [RETENTION.md](RETENTION.md) specifies transitions, uncertain outcomes, restore fencing and the SDK workflow.

A staged deployment retains the previous bundle, authorization and active schema while native source writes also maintain the proposed index definitions. `advance` scans bounded source pages, then builds adaptive batches of retained materialized roots and their dependency closures per page in a hidden graph generation. Source data is written once; mutations and managed-key changes maintain both the active and already-built target graphs atomically. Durable cursors survive restart and partition movement. `activate` requires a ready build, validates keys, refreshes clock/key-dependent work, and atomically switches code, indexes, public aliases, policy and the active graph pointer. It reuses prepared clock-independent outcomes. Each root closure and activation refresh still obey evaluation budgets, which charge the graph entries they add rather than the graph already built; graph topology validation may traverse the whole graph.

`FLOWER_DEPLOYMENT_PAGE_MS` sets the soft graph-page preparation target independently of ordinary writer batching: positive integer milliseconds, default 200, capped by the evaluation timeout. Lower targets favor more, smaller pages and shorter competing write stalls; larger targets favor fewer commits and rebuild throughput. A failed multi-root candidate can retry one root with its full normal evaluation timeout. The setting is read at server startup, so changes require a restart; it is not an HTTP request field. `maxBytes` remains the separate per-call work budget.

Fatal target errors during dual maintenance mark the job `failed` while active writes continue within normal budgets. Cancel and collect the failed build before staging corrected code. Explicit page errors preserve earlier progress for retry. `cancel` retires the deployment intent; `collect` removes obsolete or canceled graph records and index rows incrementally, protecting active generations and shared index definitions. Resolve and collect a job before starting another deployment. HTTP cancellation does not roll back committed progress. Status returns `{revision,value}` with `value` null or `{requestId,phase,baseRevision,baseBundleHash,bundleHash,cursor,scannedRows,builtEntries,generation,graphCursor,rebuiltRoots,error,cleanupCursor}`; phases are `backfill`, `rebuilding`, `ready`, `failed`, `active`, `canceled`, `collected`. Index counters measure backfill work, not distinct current index size; `rebuiltRoots` counts roots visited by graph pages, excluding roots created by concurrent writes. Use the original request ID after uncertain responses. Arbitrary source-record transformations remain explicit application migrations. See [staged deployment](INDEXES.md#resumable-staged-deployment) for the complete lifecycle.

## HTTP transport

One listener serves HTTP/1.1 and HTTP/2. Its default mode is cleartext with prior-knowledge h2c. An h2c client begins with the HTTP/2 connection preface; HTTP/1.1 Upgrade negotiation is not supported. Setting all three FLOWER_TLS_CERT_FILE, FLOWER_TLS_KEY_FILE and FLOWER_TLS_CA_FILE values enables native TLS on the same port. Route schemas, operator authentication, peer identity checks, request limits, and transactional guarantees are the same for both protocols. TLS uses h2/HTTP1 ALPN; internal HTTPS clients trust only the configured CA and verify hostnames. There is no downgrade or verification bypass. See [TLS.md](TLS.md) for trust, credentials and rotation.

Clients may send default-namespace mutations and deployments to any current member. The receiving server selects the leader and forwards the original invocation and request ID through a pooled HTTP/2 connection; callers never need to discover a leader. Public deployment authorization is checked before forwarding. Queries and watches continue to execute on the addressed replica under the deployed query consistency policy.

The internal `POST /raft/forward` route requires the peer bearer token, matching runtime compatibility, and source/target node IDs and advertised addresses from Raft membership. Its response carries the destination identity and compatibility, which the sender verifies before accepting either a receipt or an error. Its receiver is strictly leader-only and never forwards recursively. Leader changes and temporary unavailability can retry the same invocation within the configured read, commit and evaluation time budgets; an expired deadline returns `503 UNAVAILABLE`, and callers must retry an uncertain mutation with the same request ID. Permanent application errors retain their original HTTP status and JSON body. Internal identity failures return `409 FORWARD_IDENTITY_MISMATCH`, unknown sources `403 FORWARD_SOURCE_UNKNOWN`, and incompatible contracts `426 FORWARD_INCOMPATIBLE`; a mismatched peer response or oversized peer response becomes `502 FORWARD_IDENTITY_MISMATCH` or `502 FORWARD_RESPONSE_TOO_LARGE`.

Raft peers use pooled, multiplexed HTTP/2 connections (HTTPS when native TLS is configured) to their configured `host:port` addresses, retaining RPC deadlines and typed error handling. Every peer request and successful response must carry the same `x-flower-compatibility` contract: explicit wire, state-machine, snapshot and value-format versions plus the embedded QuickJS guest hash. Package build versions may differ when this contract matches. Missing or mismatching contracts are rejected before RPC processing, including on existing or restarted members. Builds predating this gate require an initial whole-cluster upgrade. See [membership and compatible rolling upgrades](MEMBERSHIP.md) for the exact contract, operator procedure and storage-migration limitations.

The default TypeScript client uses the host's `fetch`. Node.js callers can inject `createHttp2Transport().fetch` through `new FlowerClient(url, {fetch})`; the adapter is exported separately as `@flower-js/sdk/http2` and accepts `http://` or `https://` origins. It implements Flower’s JSON POST subset and streaming SSE responses, not a general Fetch API. Sessions are reused per origin, and `close()` cancels active streams and releases them. Ordinary JSON defaults are a 30-second whole-request deadline, 30-second idle timeout, at most 16 live sessions, 8 MiB request bodies, and 64 MiB buffered responses. For an SSE request, the request deadline covers response headers only; after a successful SSE response, the caller’s signal or transport closure controls lifetime. The adapter exposes a backpressured response body with a 64 KiB Web-stream queue, plus Node/HTTP2 transport buffering. SSE event/value bounds belong to the SDK parser rather than a lifetime byte cap. Non-SSE error responses retain the ordinary JSON deadline and response-size cap. Request options accept an `AbortSignal`; cancellation can leave a mutation's outcome uncertain and does not undo a committed change. The adapter performs no automatic retries, redirects, compression decoding, or HTTP/1.1 fallback. HTTPS negotiates h2 with verified TLS; optional `ca` accepts PEM strings/Uint8Arrays or arrays of either, replacing default trust roots for this transport.

## SDK descriptors

- Collection: `{kind: 'collection', name, indexes}`. `.index()` and `.key()` return new references; key and record schemas stay in the SDK and are never serialized.
- Equality query: `{kind: 'query', collection, fields, value}`. Multiple fields use a value tuple.
- Range query: `{kind: 'range', collection, fields, options}`.
- Derived definition: `{kind: 'derived', name, compute}`; aggregates add `aggregate: {collection, fields}`.
- Query method: `{kind: 'queryMethod', name, compute, consistency?}`; private until exposed in `http`.
- Mutation method: `{kind: 'mutationMethod', name, compute}`; private until exposed in `http`.
- Transaction method: `{kind: 'transactionMethod', name, compute}`; `compute` ignores its context and returns the plan `{calls, value?}`.

Tasks, triggers and components exist only in the SDK. `define` accepts `uses`, `collections`, `definitions`, `tasks`, `triggers`, `keys`, `http` and `auth`, flattens components, and returns the manifest described under privileged operations. It registers the listed definitions and every exposed method; derived descriptors cannot appear in `http`, and names or aliases beginning with `$flower.` are reserved. Method `args` schemas run inside their `compute` functions. Each mutation method is wrapped so that triggers run over the rows it changed before it returns, and trigger and aggregate sources join the collection declarations. All tasks, including those contributed by components and `materialize` policies, compile into the `$flower.maintenance` pair: the run handler receives `null`, runs the earliest-due task and returns `{task, result, $flower: {continue}}`; the error handler receives `{error: {code, message, details?}, failedAt}`. `auth` and method `access` compile into `$flower.authorize`, which receives `{credentials, method, args, partition, delegation}` and returns the admitted principal or throws. The returned manifest and its dictionaries are frozen; arbitrary exports do not expose HTTP methods.

Function code lives in bundles; descriptors crossing runtime boundaries contain no functions. Derived and query contexts expose `now`, `get`, `scan`, `range`, and `query`. Query/mutation contexts additionally expose `principal` and `history`; mutation contexts expose `set`, `delete`, `materialize`, and `unmaterialize`. Query contexts reject attempted writes, including caught attempts. SDK-bound contexts encode and decode typed keys, validate record schemas on `set`, and return `null` from `principal()` for `$anonymous`. Ordinary pure helpers may be called directly; nested public method dispatch is not implemented.

## Evaluation

The Rust evaluator coordinates graph transitions, source writes, materialized roots and privileged bundle activation. It returns `{puts, deletes, evaluated}` for a deployment and also `value` for an application method. The original JavaScript functions `flowerEvaluate` and `flowerInvoke` remain test-only reference implementations; they are not the server's coordinator.

Invocation kind and sampled epoch-millisecond time are provided by the server. Public requests cannot supply time or the internal-commit flag. The evaluator stages writes and creates lazy previews when a method reads derived values. The final graph uses only explicitly materialized roots; temporary read roots do not persist. A query always returns empty puts/deletes.

Each application callback runs in a fresh logical QuickJS-NG Wasm instance on the evaluation's blocking worker. Compiled modules and pristine initialization images are reused; mutable application memory is reset for every callback, with file-backed copy-on-write where supported. The guest imports exactly `flower.host_call` and `flower.crypto_call`. The first uses synchronous, length-delimited JSON to invoke the Rust coordinator, which tracks dependencies and can evaluate another callback in a separate guest. The second borrows validated binary spans for native NaCl/JOSE work, then copies the result into one guest-owned buffer; binary data does not traverse JSON or base64. Primitive strings support JWT claims/options/token processing. Entropy is restricted to mutation callbacks and prohibited during initialization. JWT verification/decryption read the invocation clock through the coordinator, recording its time dependency. No QuickJS value or mutable application heap crosses between instances.

Nested callbacks share an absolute execution deadline and aggregate guest-memory allowance. Rust transaction allocations have a separate budget. Wasmtime epoch interruption, the host-stack guard and instrumented guest C shadow-stack checks enforce execution and stack bounds; exhaustion remains fatal even if application code catches a JavaScript exception. QuickJS's own catchable heap/stack limits are disabled in this guest. Uncaught method exceptions abort the invocation; ordinary derived errors become outcomes. An exception's string `code` property and message form its failure, and a method failure also keeps a JSON `details` property. Without a string code, a message matching `out of memory` or `interrupted` (case-insensitively) reports `EVALUATION_BUDGET`, and anything else `COMPUTE_ERROR`. No native JavaScript engine is linked into the server.

Trusted previews reuse their private base map and track changed keys for final patches. Collection rows are sorted only when read through a scan or query. These optimizations stay within one invocation and retain source identity validation, canonical key ordering, rollback, dependency tracking, and all graph budgets.

The Rust host orders callback response object keys by JavaScript's UTF-16 comparison before encoding them. Application guests receive fresh values through JSON parsing, without another interpreted canonical traversal on every read. Numeric-index enumeration still follows JavaScript rules; key identities and persisted JSON values are unchanged. Canonicalization and persistent graph state remain under Rust's control.

The service may memoize a successful query by internal method, canonical arguments, and full admitted principal within one logical database. Every request resolves the registry, obtains its declared read fence, and runs current authorization before reuse. Native dependency certificates validate observed records, missing keys, collection/index membership, derived outcomes, code, schema and managed policy against the chosen snapshot; unrelated revisions can retain reusable results. A scan of a declared index stamps the entries in its result window: when that index changed, validation compares just those entries and, if they match, adopts the index's new version for later checks. Key-ordered scans stamp the collection's key membership, which changes only with inserts and deletes. Direct or newly evaluated derived `ctx.now()` calls, or any stored cell clock dependency, disable caching. `FLOWER_QUERY_CACHE_BYTES` bounds estimated results, keys and certificates (16 MiB per logical database by default); `FLOWER_QUERY_FLIGHT_BYTES` bounds shared-evaluation metadata (512 KiB). Zero disables either tier, and there is no fixed entry-count cap. Cache/producer waiters release their execution slot and snapshot while waiting, then reacquire admission and recheck current policy. Certificates are process-local optimization metadata and do not replace durable state or read fences.

## Time and maintenance

The leader samples time once after its quorum read and evaluation permit acquisition. `ctx.now()` returns that same nonnegative safe integer in all callbacks and previews. It is at least committed `clock`, current host wall time, and the process's observed/elapsed time floor. Successful mutations and deployments commit the sampled clock with their patches; failures commit neither. Replicas apply the concrete result without consulting their clocks. Queries use a fresh sample ephemerally, so the same source revision can yield a different time-dependent value. SSE watches emit changed values even at the same revision; the polling watcher compares both revision and value. A query-only sample is not a durable time floor across failover.

`ctx.clock()` returns the same time for code that reports, through `ctx.changesAt(time)`, every later instant at which its result can change; the earliest declared instant bounds how long the result stays exact at its revision, and past instants and `null` declare nothing. `ctx.now()` makes no such promise, and neither does a query that reads a stored derived value while any materialized cell depends on the clock. The SDK's queues, external values and expiring collections declare exact instants. Derived calls to `ctx.now()` or `ctx.clock()` record a `clock` dependency. Clock advances invalidate dependent cells and their transitive readers. Query previews recompute them without persisting. Ordinary collection reads remain unaware of TTL; TypeScript expiration helpers wrap their records and use the tracked clock. Their expiry boundary is `now >= expiresAt`, independent of physical cleanup. Lease methods likewise check owner, fencing token, and deadline inline. Deadlines use invocation time, not commit or response time; synchronized host clocks are required for accurate real-time durations.

Maintenance has no periodic poll. The SDK's composite handler returns `{"$flower":{"continue":bool,"next":ms|null}}`, when any task is next due, retry delays included, and the leader sleeps until then or until a write or leadership change may have moved a due time, never starting two runs within `FLOWER_MAINTENANCE_INTERVAL_MS` (250 ms by default). The run's evaluation records what it read, as an optimistic mutation's certificate does, so that only a later write of that database to something it read (a record, a membership, the entries in the window of a declared index its range examined) or to code, registrations or policy wakes it early; writes to anything else, and writes to the other databases of its Raft group, leave the time it declared in place. Without that record, any write of its database wakes it: while a staged deployment maintains the graph, while a stored derived value reads the clock (time alone could change what a run's preview computes), after a failed run or one whose read tracking would pass the memory budget, and after a leadership change or a lag in the server's change feed; a replaced state or an installed snapshot always wakes it. A handler that returns no `next` is polled at that interval, as are failed runs. Only the leader runs configured maintenance after a quorum read, under the same writer lock and evaluation limits as client mutations. The committed registry selects the private handler. Its final patch uses the captured revision for CAS, so an obsolete leader cannot overwrite newer state. Skipping a patch containing only the clock avoids idle writes. Other successful patches advance revision and commit clock normally. Failing handlers roll back; deployment can replace them without running the old handler. Maintenance is repeatable, best effort, and can pause under load or without quorum.

After a non-idle maintenance evaluation, a result containing `{"$flower":{"continue":true}}` requests prompt continuation against its staged patch under the same writer turn. A burst stops after an invocation takes elapsed burst time past the configurable maintenance burst duration (50 ms by default); there is no independent invocation-count limit. Each invocation is separately evaluated and sampled, with its own rollback boundary and application revision. Successful patches share a durable group commit, including a successful prefix when a later callback fails. Idle patches stop regardless of the hint. The SDK's composite handler returns it whenever another task is already due; a hand-written handler would opt in explicitly by returning it.

When a configured maintenance run fails, its entire evaluation is discarded. If `onError` is configured, the host evaluates it with a fresh runtime and resource budget against the exact original snapshot and sampled time. Its arguments are `{error: {code, message, details?}, failedAt}`. `error` is the run's failure as callers would see it: the application's code and details, `COMPUTE_ERROR`, or `EVALUATION_BUDGET` when the run exhausted its budgets. Only a failure outside evaluation, such as a panic, reports `MAINTENANCE_FAILED` with the error text. `failedAt` is a fresh server timestamp taken after failure. Keeping `ctx.now()` at the original sample allows deterministic reselection of the failed task and timer; `failedAt` lets TypeScript delay a retry from failure completion. The SDK's error handler records per-task backoff (1 s doubling to 60 s) in `$flower.tasks`, or calls the task's own `onError`. Only the successful run patch or successful error-handler patch is proposed, using the original revision CAS. Failure of the error handler itself commits nothing and is logged; it is not recursively handled. Public mutation errors do not use this recovery path.

## Scheduled callbacks

`@flower-js/sdk/scheduler` implements durable timers entirely as TypeScript records and one task in the SDK's composite maintenance handler. `after` computes a deadline from `ctx.now()`; `at` accepts an absolute deadline. Registering, replacing, or cancelling a timer uses the calling mutation's ordinary writes and therefore commits atomically with business data. The timer ID is the replacement key. There is no host-side deletion rule or timer-specific Raft command.

The scheduler selects one pending, due timer by `(dueAt, id)` from the captured snapshot, when the composite handler selects its task. It deletes the timer before invoking its registered synchronous mutation callback, allowing that callback to schedule its own next occurrence under the same ID. Successful callback effects, derived updates, and consumption of that timer publish together. A failed callback's writes are discarded before the error handler reselects the same task and the scheduler's `onError` reselects the same original timer, records the failure `{code, message, details?}`, and schedules a bounded retry or retains a terminal failed record. Newly due timers cannot replace the original selection during error handling because the snapshot and `ctx.now()` are unchanged. Handler aliases are resolved through deployed TypeScript code, independently of the HTTP allowlist.

Failover can repeat evaluation before a commit, but revision CAS and atomic timer consumption prevent duplicate committed effects for one pending timer. Scheduling a new generation with the same ID is a new action. Time is a lower bound for dispatch, not a latency guarantee. Each maintenance invocation handles one timer, selected through the `(state, dueAt)` index. Successful timers are removed rather than retained as history; failed timers can be inspected, cancelled, or explicitly retried. External effects should be represented by work queued transactionally for workers.

## Durable keys

The application state is an ordered map from strings to JSON values:

- `source:` + canonical `[collection, key]` → record value
- `cell:` + canonical `[definitionName, args]` → `{name, args, outcome, deps}`
- `root:` + canonical `[definitionName, args]` → `{name, args}`
- `reader:` + dependency ID + NUL + cell ID → `null`, one for each non-scan dependency of a stored cell
- `height:` + cell ID → the number of cells on its longest derived path, itself included; absent for cells that read no other cell
- `bundle` → `{hash, javascript}`
- `httpMethods` → `{publicAlias: {name: internalName, kind: 'query' | 'mutation' | 'transaction', consistency?}}`
- `maintenanceMethod` → `null` or `{name: internalName, kind: 'mutation', onError?: {name: internalName, kind: 'mutation'}}`
- `authorizationMethod` → `null` or `{name: internalName}`
- `clock` → last committed sampled epoch milliseconds

Canonical JSON sorts object keys lexically, preserves array order, and uses JavaScript JSON number semantics. Omitted instance arguments become `null`.

Outcomes are `{ok:true,value}` or `{ok:false,error:{code,message}}`; stored derived errors never keep failure details. Dependencies are source IDs, derived cell IDs, `clock`, or `collection:` + JSON-encoded collection name. Missing source reads are dependencies. Scans/equality queries depend conservatively on the complete collection. Successful evaluation replaces dependencies; errors retain the union of prior and observed reads. Reachability from roots controls derived-cell collection: a cell with no root and no reader record is deleted with its own reader and height records. The engine writes reader and height records in the same patch as the cells they describe; a change propagates to a dependency's readers by prefix, and heights above 128 are rejected.

The SDK's helpers store ordinary source records; typed keys are stored as canonical JSON text. Expiration envelopes contain `{value, createdAt, updatedAt, expiresAt}`. Queue jobs are keyed by `[scope, id]` in the queue's collection and contain `{scope, id, payload, state, availableAt, leaseExpiresAt, lease, attempts, createdAt, updatedAt, result, error, priority, group, turn, queued}`; records written before `priority` existed lack the last four and are claimed as priority 0 ahead of newer jobs. Collection `$flower.turns` keeps, per canonical `[queue, scope, priority]`, the last claimed turn, and per `[queue, scope, priority, group]` the group's next turn while it has jobs queued. Owners waiting for work live in `<queue>.line`, keyed `[scope, owner]`, as `{scope, owner, room, since, expiresAt}`. A lease contains `{owner, token, expiresAt, history?}`. When retry retention is initialized, history records its logical database/incarnation; renewal, completion and failure must supply the matching current history. Collection `$flower.fencing` keeps one counter per queue and scope, keyed by canonical `[queue, scope]`, which retains the last issued token even when work is replaced or deleted. Internal application code must preserve these counters to preserve fencing. Timers live in the collection named after their scheduler. `define` reserves `$flower.tasks` for per-task maintenance backoff and `$flower.materialized` for materialization progress; external values keep `<name>.results` and, with `each`, `<name>.stale`.

## Consensus commands

A commit contains `request_id`, `fingerprint`, `expected_revision`, `puts`, `deletes`, `result`, and `internal` (default `false`). The HTTP layer first checks that the requested alias is currently exposed with the correct kind. State-machine application checks request receipts before the expected revision. A same-content retry returns its original revision and result; changed content using the same ID is rejected. Fingerprints include the public alias, arguments, and supplied expected revision, so retries through `/v1/call` and `/v1/mutate` agree. Internal maintenance commits skip receipt lookup and storage, but still enforce CAS and advance application revision. Accepted commits increment the application revision once. Raft configuration/no-op entries and rejected commands do not increment it.

A log command is a single commit, a leadership-fenced commit, or `{batch: {expected_revision, puts, deletes, items}}`. A batch carries only its final key overlay; every item retains `{request_id, fingerprint, result, internal?}` in invocation order. Repeated updates to one hot value therefore serialize and replicate that value once. The constructor requires contiguous proposed revisions and unique external request IDs. The state machine validates the whole command, checks all receipt conflicts and the base revision, and reserves the complete revision range before changing any data or receipt. A failed precondition rejects the whole batch. A batch whose every item already has a matching external receipt returns those original outcomes without applying its overlay; a partially matching batch is rejected and must be rebased. Internal items consume a revision without creating a receipt, and cannot participate in a duplicate-only replay. Successful items keep their individual revisions and results; no intermediate key state is published.

The writer accepts methods in order against private staged state and filters same-ID retries before constructing the compact batch. Bounded parallel candidates may prepare against one immutable base; their native certificates and current authorization must validate against preceding staged changes, otherwise they rerun. Discarded candidates publish neither data nor entropy/results. Failed method evaluations add no command. Batch preparation duration, queue admission, and encoded transaction/RPC budgets are operator settings. The default adaptive controller learns per-call preparation cost and durable commit time, increases its preparation window under queued load, and shrinks it as those costs fall. The configured preparation duration and admission capacity bound each adaptive group; an optional explicit batch count supplies another hard cap. Fixed-count mode remains available for controlled comparisons. Idle requests start immediately, and late arrivals coalesce only during an existing predecessor commit. DEBUG group events record decisions, targets, queue pressure and actual timings. Admission conservatively uses individual command sizes; consensus checks the exact compact payload against `FLOWER_TRANSACTION_MAX_BYTES`. Responses wait for durable quorum commitment and local group application. A leadership/CAS failure returns a retryable error, and same-ID retries resolve already committed results. Cross-group prepare commands additionally bind the complete Raft leader identity that authorized the prepare; applying them under a different leader rejects them even if the application revision has not changed.

Under sustained load, the writer may prepare one successor group against the private post-commit state of its predecessor while that predecessor commits. It submits the successor only after confirming the predecessor's exact durable results. Failure or uncertainty discards the successor, including dependent replay and validation responses, and requires a fresh quorum read before more preparation. Speculative state is never published to queries or watches. Deployments run alone, and scheduled maintenance runs between drained writer windows.

The receipt map stores `{fingerprint, revision, result}`. Snapshots include it along with the application keyspace, last applied index, and membership. State and applied index are updated in one atomic checkpoint transaction. The leader only acknowledges after durable Raft quorum commitment and local application. Linearizable queries use OpenRaft's quorum barrier before capturing state.

The on-disk store uses redb tables `raft_meta_v1` and `raft_logs_v1`, plus `application_data_v4` and `application_requests_v4` for individual records and receipts. Named partitions keep theirs in `logical_partition_data_v3`, `logical_partition_requests_v3`, `partition_copy_base_data_v3`, `partition_copy_base_requests_v3` and `partition_difference_chunks_v3`, keyed by partition then key. Keys are UTF-8 stored as bytes, which redb compares as they are. A stored value is its write's version, eight little-endian bytes, followed by its JSON. Versions identify writes, never order them; dependency certificates compare them, and a record keeps its version between memory and disk. Replicas serve these tables from redb read snapshots. Memory holds only the writes still queued for disk, as a tree over the snapshot in which deletions are tombstones, plus a cache of parsed values bounded by `FLOWER_VALUE_CACHE_BYTES` (default 256 MiB). An apply that finds persistence has advanced moves the state onto a newer snapshot and drops the entries whose write it holds: a value found there at its version, or any write whose queued batch is written. An apply publishes changed keys and new receipts with revision, membership, and applied-index metadata in memory, then queues them; one background task writes queued states in apply order, each batch in one atomic `Durability::None` redb transaction. Publication and queueing happen together, even if the awaiting task is cancelled, and neither waits for the disk. This checkpoint does not require an immediate fsync; subsequent Immediate log, vote, snapshot, or purge transactions make prior written checkpoints durable. A failed write stops every later write and fails the next apply; recovery replays from the last written state. Acknowledged mutations remain recoverable from the quorum-durable Raft log. Raft snapshot construction captures immutable roots at an applied log position, waits until the queued states up to it are written, and commits a small metadata checkpoint with Immediate durability. This flush makes the existing application tables durable before Raft can prune their source logs; no second full-state image is stored. A transfer image is encoded only when a peer reads it, outside the apply lock and storage write gate, and streams to the peer as it encodes. The sender finds its end by reading to it, and keeps the segment it last read so a failed segment can be resent; starting over encodes the image again, and only a request for its size encodes it to an anonymous temporary file. Generation checks stop an older builder from publishing over a newer install. Installation validates the complete JSON state and matching Raft metadata, then atomically replaces the application tables and checkpoint metadata with Immediate durability. On restart, the transfer image is reconstructed lazily from the durable application tables; if those tables are ahead of the recorded checkpoint, its metadata advances to match the recovered state. State behind the checkpoint or purged log position fails recovery. Installation decodes the received file into a temporary spool file in the database directory, so its size is not bounded by memory. Each map of records must arrive in strictly increasing key order; it is appended as one run with every 64th key indexed in memory. Installation then copies the spool into the application tables and serves them. Follower log appends, votes, snapshot publication/installation, and log purging retain Immediate durability; purging and installation first wait for queued application writes. Application checkpoints defer their flush, and so does a leader of at least three voters for its own log appends: it counts toward the commit quorum only after one Immediate commit, 30 ms after an append stays uncommitted and otherwise at most every 500 ms, makes them durable (see [bench/ARCHITECTURE.md](bench/ARCHITECTURE.md)). A crash can therefore leave a leader with an older log than its followers, so a restarting node reloads its own committed vote as uncommitted: it keeps its term and vote but must win a later term before leading, instead of appending new entries under log ids its followers already hold. A follower receiving a snapshot accepts the leader's vote with every chunk, and while the install runs, so a transfer longer than the election timeout does not start an election that restarts it. Snapshot scheduling supplements the native entry-count trigger with applied durable-log bytes and nonidle age. Only the supplemental triggers use measured build-time cooldown; entry-count/manual triggers remain independent. Byte accounting restarts from durable log lengths, while age uses a new monotonic origin on process restart. Snapshot publication removes only the captured byte prefix, preserving accounting for concurrent applies.

If the durable log extends beyond the recovered applied position, startup arms one serving barrier shared by the physical node and its logical partitions. Before serving read fences or writer baselines, a recovering leader quorum-commits and applies an internal `{recovery_barrier:null}` Raft command. It advances only the applied log position, preserving application revisions, data and receipts. A heartbeat proof alone is insufficient when the persisted leader resumes the same term with a checkpoint behind its durable logs. Followers wait for local application through a fresh leader fence. Application snapshot access, including replica-local queries and watches, waits for this recovery. A failure reports startup recovery unavailability or timeout. Peer RPCs, initialization, and diagnostic snapshot/status access do not require this barrier. After recovery, replica-local reads retain their usual no-per-read-quorum semantics. A durable but uncommitted log tail is never blindly replayed as committed work. Recovery barriers are physical-group controls and cannot be nested inside partition-scoped commands.

Within a supported redb file format, opening a database with the old application-blob layout atomically migrates that blob to these tables. Checkpoint metadata similarly migrates forward to the current version, replacing the prior metadata with a retirement marker that older binaries reject. The state-machine compatibility contract covers the recovery policy and versioned materialized graphs: pre-change and current nodes cannot form a mixed cluster, and downgrading the migrated directory is unsupported. Older binaries reject the resulting retired-blob marker. This internal layout conversion does not upgrade unsupported legacy redb file versions, which are rejected; there is no storage-upgrade tool or general compatibility promise for older Flower directories. Previous JSON-envelope, binary and raw/LZ4 `FLOWERSNAP3` snapshot images remain readable. The first new checkpoint atomically retires that duplicate image and its chunk table. Snapshot transfer retains the existing JSON state format, including records, indices, materialized values, receipts and partition state. The metadata-only checkpoint adds no new wire format. Snapshot encoding is independent of the compact command format. Nodes require matching wire and state-machine compatibility contracts. JSON records and results retain bounded parsers independently of their transport wrappers, so a valid deep value remains readable after replication or snapshot recovery. Node identity is persisted, and a directory cannot be opened under a different node ID. A process hosting several replicas (`--replica NAME,ID,LISTEN`) keeps them in one database, prefixing each replica's tables with `NAME/`; the empty prefix is the single-replica layout above, and neither kind of directory opens as the other. Hosted replicas' log appends and applied-state writes share batched transactions: a batch that contains a durable write commits with Immediate durability once for all of them. A write that fails while being staged aborts only its own batch attempt; the others are staged again in a new transaction. Batches commit in submission order, so every replica, hosted or not, queues its log appends and applied-state writes without waiting for earlier ones to commit, while log readers merge the queued appends with committed ones. A replica's direct transactions (votes, truncation, purges, snapshot publication and installation) first wait until its queued writes have committed. Storage adapters pass OpenRaft's conformance suite; integration tests exercise actual HTTP replication, snapshot catch-up, restart, failover, and loss of quorum.


## Logical partitions and ownership routing

A physical Raft group can host many independently revisioned logical partitions. Each partition contains its full records and receipt history, including the deployed bundle, maintained graph/index state, timers, leases and their fencing counters. Scoped application commands carry the partition ID and ownership epoch. The state machine checks that the partition is active at that epoch before checking a receipt or applying a CAS; a retired source cannot replay an old receipt as a successful current-owner request.

Stable routes use `/partitions/{partition}/v1/{call,query,mutate,watch,identity,session}` and `/partitions/{partition}/admin/{deploy,keys,retention,transactions}`. The server resolves the durable catalog placement and includes its epoch in the internal invocation. A group's registered addresses are discovery seeds: catalog/control requests can obtain an authenticated current-leader hint, and application writes reaching an owner follower hop once to the leader from that member's Raft membership. The authenticated leader hop binds both node IDs and advertised addresses, preserves the original partition/epoch/invocation, and cannot recurse after a leadership change. Query calls and watches execute on the receiving owner replica under their declared consistency policy. Internal invocation responses identify Unicode group names using `x-flower-group-sha256`, the lowercase SHA-256 digest of the exact UTF-8 name.

Movement is a durable roll-forward protocol: record a copying phase in the catalog, persist an immutable source base while the source keeps serving, import bounded ordered chunks into invisible destination state, then freeze the source at its expected revision. Transfer the difference from the captured base to frozen state, including data and receipt deletions, or fall back to a full frozen image when the difference is larger or exceeds the configured tail budget. A copied base is explicitly not activatable: only sealing and verifying the final quiescent image permits catalog cutover and destination activation. Source retirement preserves the ownership tombstone and removes the captured base. Every control command checks its operation ID, transfer identity and expected ownership phase; controls authorized after a catalog observation are fenced to the full Raft leader identity. No timeout unfreezes a source or reverses catalog cutover. Source freeze rejects unresolved participant/coordinator transactions. Logical transaction targets resolve and pin their physical group and placement epoch before preparation; completion and recovery remain routable while freeze waits. Retry/session metadata, key policy and transaction closure metadata travel with the partition. Destination key material must be unlockable before cutover.

Serving catalog placements include active ownership and a move’s live-copy phase. After copying, movement gates ordinary requests until activation. Only serving placements are cached. Fresh reads retain quorum and native epoch checks; explicitly replica-local reads may lag ownership within the configured placement-cache interval. An old watch must refresh that ownership observation and terminate on movement, changed ownership or an unavailable catalog rather than streaming indefinitely from a retired source. A reconnect to the stable URL starts with a new complete snapshot.
